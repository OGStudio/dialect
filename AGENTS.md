# Dialect

Declarative reactive state management for macOS. This is a **new Swift port ("v4")** of the Kotlin Dialect (KD) controller & Klin code generator. Business logic is defined in YAML ("dialect") and executed by a Swift runtime.

**SYMLINK PARITY RULE**: There is ONE `components/` dir at the repo root holding the source-of-truth for BOTH the generator's components (`cli/`, `yml/`, `swift/`, `kotlin/`, `llm/`, `net/`, `agent/`, `conv/`, `transpiler/`, `other/`) AND the example's (`root/`, `other/`). Every consuming tree gets SYMLINKS; nothing is copied. Whenever a new `components/<group>/<file>.swift` is added, create a matching symlink in EVERY tree that needs it, or the build won't see it (the file is simply not compiled). Component groups live under their own dirs under `src/`: `cli/`, `yml/`, `kotlin/`, `llm/`, `net/`, `agent/`, `conv/`, `transpiler/`, `other/`.

**Symlink depths (all roots are symlinks — 4 `../` from `ver-mac/src/<group>/`)**:

|---|---|---|---|
| Generator | `generator/ver-mac/src/<group>/<file>` | **4** | `ver-mac/src/yml/ymlConst.swift -> ../../../../components/yml/ymlConst.swift` |
| Agent | `agent/ver-mac/src/<group>/<file>` | **4** | `ver-mac/src/llm/llmAux.swift -> ../../../../components/llm/llmAux.swift` |
| Example macOS | `example/ver-mac/src/<group>/<file>` | **4** | `example/ver-mac/src/root/root.swift -> ../../../../components/root/root.swift` |
| Example macOS view | `example/ver-mac/src/root/view/<file>` | **5** | `.../root/view/RootView.swift -> ../../../../../components/root/mac/view/RootView.swift` |
| Example iOS | `example/ver-ios/src/<group>/<file>` | **4** | same as macOS |

The Android depth is the error-prone one — the path is `ver-android/app/src/main/kotlin/org/opengamestudio/<group>/`, which is 9 dirs below the repo root. Gradle/AGP does follow symlinked sources, but the symlink must exist or the file is simply not compiled. Note the example targets reference `components/root/android/` and `components/other/` (NOT `components/root/`) for their Kotlin files, and `components/root/mac/` vs `components/root/ios/` for the per-platform Swift views.

**After ANY move of `components/` (or a subdir), audit for dangling links — `find . -type l ! -exec test -e {} \;`** (exclude `.build/`). A symlink pointing at a deleted path does NOT fail loudly: SPM/Gradle just skip it, so a moved-away component can vanish from a build with no error. `util/paths` (`GENERATOR_COMPONENTS`) is also a hardcoded path that must be repointed when `components/` moves — `util/build-generator` fails with a bare "No such file or directory" from `util/step/embedCoreKotlin` when it is stale.

## Key Concepts

- **DialectContext**: Protocol for typed field access by string name
- **DialectController**: Reactive engine — queue field mutations, process cascade
- **dialect.yml**: Declarative rules with `should` blocks, `if`/`then` conditions, plus `oneliners` mapping field-changes to effect/UI callbacks (e.g. `readFile: cliReadInputFile(c.inputFileName)`)
- **Oneliner effects**: registered via generic `registerOneliners<T>(ctrl, items:[Any]) -> T?` (from ref/kom) where items are `[fieldName, (T)->Void, ...]`; caller pins T via `let _: CLIContext? = registerOneliners(...)`. Effect funcs call `cliSet(field, value)` to push results back into the context, expanding the cascade. **IMPORTANT (Void-closure constraint)**: each callback is cast `as! (T) -> Void`, so a reaction that is a single optional-chaining *expression* (e.g. `RootVM.shared?.countText = c.countText`) infers closure type `(T) -> Void?` and crashes the cast at runtime. Reactions touching a weak/optional singleton MUST therefore force-unwrap instead (e.g. `RootVM.shared!.countText = c.countText` — safe here because `RootVM()` is created before `root.setup()`). A statement body (`if let vm = RootVM.shared { vm.countText = c.countText }`) also works (returns `Void`).
- **Multiple components**: each component (CLIComponent, YMLComponent, SwiftComponent) owns its own context + controller and registers its own oneliners/shoulds. **Cross-component bridging** is done via oneliners in the source component, e.g. CLI's `inputContents` oneliner calls `ymlSet(F.inputContents, c.inputContents)` and YML's `entities` oneliner calls `swiftSet(F.entities, c.entities)` to push values into the YML/Swift controllers (`F` field-name constants are shared/global). Each component's init must call `xxxRegisterEffects(ctrl)` (oneliners) and `xxxRegisterShoulds(ctrl)`. Swift's `out` oneliner calls `otherWriteFile(c.path, c.out)` (needs `path` field in SwiftContext).
- **`outStructs` (v4-specific, separate from `out`)**: `SwiftContext.outStructs` holds the generated *plain struct-declaration text*, produced by the `outStructs` should: when `c.recentField == F.entityFieldTypes`, `c.outStructs = swiftStructs(c.entities, c.entityTypes, c.entityFields, c.entityFieldTypes)` and `recentField` becomes `F.outStructs`. Concatenated into `out` after `outFields`. The `swiftStructs` fun (in `components/swift/swiftFun.swift`, 4 params: `entities [String]`, `entityTypes [Int:String]`, `entityFields [Int:[String]]`, `entityFieldTypes [Int:[Int:String]]`) filters entities by `entityTypes[id] == SWIFT_TYPE_STRUCT` ("struct"), then for each struct entity calls `swiftStruct(name, fields, fieldTypes)` which emits a plain `struct <Name> { var <field> = <Type>() ... }` — NO DialectContext conformance, NO recentField. The `entityTypes` dict drives which entities become plain structs vs components vs contexts. Templates: `SWIFT_STRUCT_T` (uses `%FIELDS%` placeholder, not `%ITEMS%`), `SWIFT_STRUCT_FIELD_T` (uses `%NAME%` + `%DEFAULT%`), `SWIFT_TYPE_STRUCT` ("struct").
- **`outShoulds` (v4-specific, parallel to `outStructs`/`outContexts`)**: `SwiftContext.outShoulds` holds the generated *should-function text*, produced by the `outShoulds` should: when `c.recentField == F.entityShouldBranches`, `c.outShoulds = swiftShoulds(c.entities, c.entityShoulds, c.entityShouldBranches)` and `recentField` becomes `F.outShoulds`. Concatenated into `out` after `outContexts`, so should funcs ARE generated into `dialect.swift` (no hand-written mirror needed in tmp since the `out` should). The `swiftShoulds` fun (in `components/swift/swiftFun.swift`, 3 params: `entities`, `entityShoulds [Int:[String]]`, `entityShouldBranches [Int:[Int:[ShouldBranch]]]`) collects entity ids with non-empty `entityShoulds` via `entityShoulds.keys.sorted()`, then for each should calls `swiftShould(name, contextName, branches)`. Func name = `prefix + SWIFT_SHOULD_RESET + otherCapitalize(should)` where `prefix` = contextName minus `SWIFT_SUFFIX_CONTEXT` lowercased (e.g. `cliShouldResetConsoleOutput`). Each branch emits a condition/reaction block; conditions/reactions are multi-line arrays joined via `swiftFormatShould` (8-space base indent preserving continuation). Templates: `SWIFT_SHOULD_T` (`%FUNC%`/`%CONTEXT%`/`%BRANCHES%`), `SWIFT_SHOULD_BRANCH_T` (`%ABOUT%`/`%CONDITION%`/`%REACTION%`/`%FIELD%`), `SWIFT_SHOULD_INDENTATION` ("        "), `SWIFT_SHOULD_RESET` ("ShouldReset").
- **`outContexts` (v4-specific, parallel to `outStructs`)**: `SwiftContext.outContexts` holds the generated *DialectContext struct-declaration text*, produced by the `outContexts` should: when `c.recentField == F.entityFieldTypes`, `c.outContexts = swiftContexts(c.entities, c.entityTypes, c.entityFields, c.entityFieldTypes)` and `recentField` becomes `F.outContexts`. Concatenated into `out` after `outStructs`. The `swiftContexts` fun filters entities by `entityTypes[id] == SWIFT_TYPE_CONTEXT` ("context"), then for each context entity calls `swiftContext(name, fields, fieldTypes)` which emits a full `struct <Name>: DialectContext { var <field> = <Type>() ... var recentField = "" func field<T>... mutating func setField... }`. Templates: `SWIFT_CONTEXT_T` (uses `%ITEMS%` + `%GETTERS%` + `%SETTERS%`), `SWIFT_CONTEXT_FIELD_T` (uses `%NAME%` + `%DEFAULT%`), `SWIFT_CONTEXT_GETTER_T` (uses `%NAME%`), `SWIFT_CONTEXT_SETTER_T` (uses `%NAME%` + `%TYPE%`), `SWIFT_TYPE_CONTEXT` ("context").
- **`outSets` (v4-specific, parallel to `outShoulds`)**: `SwiftContext.outSets` holds the generated *`<component-prefix>Set()` function text* (e.g. `cliSet`/`swiftSet`/`ymlSet`/`rootSet`), produced by the `outSets` should: when `c.recentField == F.entities`, `c.outSets = swiftSets(c.entities)` and `recentField` becomes `F.outSets`. Concatenated into `out` after `outContexts` and before `outShoulds`, so Set funcs ARE generated into `dialect.swift` (no hand-written mirror in tmp). `swiftSets` (in `components/swift/swiftFun.swift`, 1 param: `entities [String]`) filters entities by `hasSuffix(SWIFT_SUFFIX_COMPONENT)` ("Component") and calls `swiftSet(entity)` per component. Func name = `prefix + SWIFT_SET_SUFFIX` ("Set") where `prefix` = contextName minus `'Context'` lowercased (e.g. `CLIComponent` → `cliSet`). Template: `SWIFT_SET_T` (`%FUNC%`/`%COMPONENT%`). Registers nothing; effects/components call these generated funcs directly.
- **Kotlin `outSets` (parallel to the Swift one)**: `KotlinContext.outSets` holds the generated *Kotlin* `<component-prefix>Set()` function text, produced by the `outSets` should: when `c.recentField == F.entities`, `c.outSets = kotlinSets(c.entities)` and `recentField` becomes `F.outSets`. Concatenated into `out` after `outContexts` and before `outShoulds`. `kotlinSets` (in `components/kotlin/kotlinFun.swift`, 1 param: `entities [String]`) mirrors `swiftSets`: filters entities by `hasSuffix(KOTLIN_SUFFIX_COMPONENT)` ("Component") and calls `kotlinSet(entity)` per component; `kotlinSet` derives the func name as `prefix + KOTLIN_SET_SUFFIX` ("Set") from `kotlinContextName(entity)` (Component→Context) minus `'Context'`, lowercased. Templates: `KOTLIN_SET_T` (`%FUNC%`/`%COMPONENT%`). The body is LIVE — `%COMPONENT%.ctrl.set(key, value)`. It used to be commented out (`//%COMPONENT%.singleton!!.ctrl.set(key, value)`, back when generated Kotlin component classes with a `singleton` did not exist), but that changed when `components/root/android/root.kt` became a hand-written `object RootComponent` exposing a `ctrl` property — see the Android port bullet. Consequence: `rootSet(F.didClickIncrement, true)` from `RootView.kt`'s Button genuinely drives the engine now, and the should *bodies* and effect *reactions* are real transpiled Kotlin (see the Conv pipeline bullet), so the whole loop runs end to end. `KotlinComponent` has no `type: kotlin` entry in the generator's `dialect.yml` `output:` section, so `c.path` stays empty and `otherWriteFile` is a no-op — the generator's own Kotlin `out` is only visible via console logging (the example's Kotlin target IS written, because `example/dialect.yml` declares `ver-android/.../dialect.kt: type: kotlin`).
- **Kotlin `outFields` (parallel to the Swift one)**: `KotlinContext.outFields` holds the generated *Kotlin* `object F` field-name-constant text, produced by the `outFields` should: when `c.recentField == F.entityFields`, `c.outFields = kotlinFields(c.entityFields)` and `recentField` becomes `F.outFields`. Concatenated into `out` BEFORE `outSets`, so the emitted `F` is available to the Set funcs and to hand-written Kotlin component code (e.g. `rootSet(F.didClickIncrement, true)`). `kotlinFields` (in `components/kotlin/kotlinFun.swift`, 1 param: `entityFields [Int:[String]]`) mirrors `swiftFields` exactly — collects field names into a `Set<String>`, emits `KOTLIN_FIELD_T` per name in `names.sorted()`, wraps them via `KOTLIN_FIELDS_T`. `struct F`/`static let` become `object F`/`const val`. Templates: `KOTLIN_FIELDS_T` (`%ITEMS%`), `KOTLIN_FIELD_T` (`%NAME%`). The `out*` sections are all populated now: `outFields`, `outStructs`, `outContexts`, `outSets`, `outShoulds`, `outRegisterShoulds`, `outRegisterEffects`.
- **Kotlin `outStructs` (parallel to the Swift one)**: `KotlinContext.outStructs` holds the generated *Kotlin* `data class` declarations, produced by the `outStructs` should: when `c.recentField == F.entityFieldTypes`, `c.outStructs = kotlinStructs(c.entities, c.entityTypes, c.entityFields, c.entityFieldTypes)` and `recentField` becomes `F.outStructs`. Concatenated into `out` BETWEEN `outFields` and `outSets`, mirroring the Swift order (`outFields + outStructs + outContexts + outSets`).
- **Kotlin type mapping (no Swift equivalent)**: the dialect's type spelling is valid Swift but NOT valid Kotlin, so `outStructs` needs two mappers that `swiftStruct` never had: `kotlinType` (`Bool` → `Boolean`; `[X]` → `Array<kotlinType(X)>`; `[K: V]` → `Map<kotlinType(K), kotlinType(V)>`; anything else passes through — `String`/`Int`/`OutputPath` are already valid Kotlin) and `kotlinTypeDefaultValue` (`""`/`0`/`false`, `arrayOf()` for a bracketed type without a `:`, `mapOf()` for one with a `:`, `%TYPE%()` for a bare named type). `Bool` is the only primitive that actually changes, which is why `KOTLIN_TYPE_BOOL = "Bool"` exists next to `KOTLIN_MAPPED_BOOL = "Boolean"` (the `KOTLIN_TYPE_*` family holds dialect spellings, `KOTLIN_MAPPED_*` holds Kotlin spellings). `KOTLIN_MAP_T` uses two placeholders (`%KEY%`/`%VALUE%`), NOT `%TYPE%` twice — `replacingOccurrences` replaces ALL occurrences, so a repeated placeholder would map key and value to the same type.
- **`kotlinTypeParts` must count bracket depth**: the dialect nests (`[Int: [Int: [ShouldBranch]]]` → `Map<Int, Map<Int, Array<ShouldBranch>>>`), so splitting on `":"` naively yields 3 parts instead of 2. It walks the string tracking `[`/`]` depth and only splits at depth 0, trimming the space after each colon via `drop(while: { $0 == " " })`. Templates: `KOTLIN_STRUCT_T` (`%NAME%`/`%FIELDS%`), `KOTLIN_STRUCT_FIELD_T` (`%NAME%`/`%TYPE%`/`%DEFAULT%`, trailing comma so the list is valid Kotlin), plus `KOTLIN_LIST_T` (`%TYPE%`) and `KOTLIN_MAP_T`. The `%FIELDS%`-on-its-own-line shape (inherited from `SWIFT_STRUCT_T`) leaves a cosmetic blank line before the closing `)`: `SWIFT_STRUCT_T` does the same in Swift, so the two ports match.
- **Kotlin `outContexts` (parallel to the Swift one)**: `KotlinContext.outContexts` holds the generated *Kotlin* `data class` context declarations, produced by the `outContexts` should: when `c.recentField == F.entityFieldTypes`, `c.outContexts = kotlinContexts(c.entities, c.entityTypes, c.entityFields, c.entityFieldTypes)`. Concatenated into `out` AFTER `outStructs`, mirroring Swift's `outFields + outStructs + outContexts + outSets`. `kotlinContexts`/`kotlinContext` mirror `swiftContexts`/`swiftContext` (same 4 params, filters by `KOTLIN_TYPE_CONTEXT`, same `%ELSE%` first-branch-omits-`else` trick), but there are three Kotlin-specific differences Swift never had:
  - **`override var recentField: String = ""` is a CONSTRUCTOR PARAM, not a body property.** Swift structs are value types so a whole-struct copy carries `recentField` for free; a Kotlin `data class` `copy()` only copies constructor params, and `DialectController` relies on `f(context.selfCopy())` seeing the *current* `recentField` (every should's first branch is `if c.recentField == F.x`). As a body property it would go stale and every should would miss its trigger. Being a param also gives the no-arg constructor for free (Kotlin synthesises one when all params have defaults), which is what `DialectController(KotlinContext())` needs — and it keeps a field-less context valid.
  - **`selfCopy()` is NOT defaulted in the Kotlin core.** `core/kotlin/DialectContext.kt` implements only `fieldAny` with a body; `selfCopy()` is an abstract member, so the generated class must provide `override fun selfCopy(): DialectContext = this.copy()`.
  - **`@Suppress("UNCHECKED_CAST")` goes on the CLASS, once — not on `field` and `setField` separately.** `as T` is unchecked, and so is `value as Map<Int, String>` / `value as Array<String>` in `setField` — erasing to a *generic* type is unchecked, so a `Boolean`/`String`/`Int` setter is warning-free but every `Array`/`Map` field warns. One annotation above `data class %NAME%(` covers every member; annotating only `field` still left ~10 warnings for `KotlinContext`, and annotating each function is noise. Templates: `KOTLIN_CONTEXT_T` (`%NAME%`/`%FIELDS%`/`%GETTERS%`/`%SETTERS%`), `KOTLIN_CONTEXT_FIELD_T` (`%NAME%`/`%TYPE%`/`%DEFAULT%`), `KOTLIN_CONTEXT_GETTER_T` (`%ELSE%`/`%NAME%`), `KOTLIN_CONTEXT_SETTER_T` (`%ELSE%`/`%NAME%`/`%TYPE%` — the `%TYPE%` is the MAPPED Kotlin type here, unlike `swiftContext` which passes the dialect type through verbatim). The `%FIELDS%` line also leaves the same cosmetic blank line before `override var recentField` that Swift has before its `var recentField`.
- **Kotlin `outShoulds` (parallel to the Swift one)**: `KotlinContext.outShoulds` holds the generated should-function text, produced by the `outShoulds` should: when `c.recentField == F.transpiledShouldBranches`, `c.outShoulds = kotlinShoulds(c.entities, c.entityShoulds, c.transpiledShouldBranches)`. Concatenated into `out` after `outSets`, mirroring the Swift order. `kotlinShoulds`/`kotlinShould` (in `components/kotlin/kotlinFun.swift`, 3 params: `entities`, `entityShoulds [Int:[String]]`, `entityShouldBranches [Int:[Int:[ShouldBranch]]]`) mirror `swiftShoulds`/`swiftShould` — same `keys.sorted()` collection, same func name `prefix + KOTLIN_SHOULD_RESET + otherCapitalize(should)` — but emit the transpiled Kotlin (below), joining the line arrays via `kotlinFormatCode(lines)` = `lines.joined(separator: "\n")`.
  - **THE KOTLIN BRANCHES ARE REAL TRANSPILED KOTLIN, NOT NO-OPS.** Earlier versions emitted each branch as `if (false) { /** <swift> */ }`, with the Swift source kept verbatim in `/** */` block comments; that is GONE (`kotlinFormatShould` no longer exists — it is `kotlinFormatCode` now). The `outShoulds` should keys on `F.transpiledShouldBranches`, the LLM-transpiled Kotlin produced by the Conv pipeline (see the Conv bullet), and `kotlinShould` emits `%CONDITION%`/`%REACTION%` verbatim. So `rootShouldResetCount` really does `c.count += 1` and the engine's shoulds genuinely run/re-queue. The "un-comment in place" / `if (false)`→`if (true)` porting story no longer applies.
  - **The transpiled condition/reaction lines arrive UNINDENTED (column 0).** The queue frames each body with an 8-space indent on the way out, but the model returns stripped lines, so in `KOTLIN_SHOULD_BRANCH_T` the `%CONDITION%` (right after `    if (`) and `%REACTION%` (right after `    ) {`) land at column 0, while the template's own `c.recentField = F.%FIELD%` / `return c` / `}` keep their 8/4-space indents. The generated Kotlin compiles but is cosmetically ragged (see the emitted `rootShouldResetCount`).
  - **`val c = c` NOT `var c = c`**: Swift needs `var c = c` to mutate its struct copy; a Kotlin `data class` copy is itself mutable (`recentField` is a `var` constructor param), so `val` is correct and mirrors intent better. The generated signature is `fun %FUNC%(c: %CONTEXT%): %CONTEXT%` — Kotlin has no argument labels by default, hence no leading `_` where Swift writes `_ c: CLIContext`.
  - The `%ABOUT%` marker uses `//` (a `//` comment survives fine as a single line) where the Swift template uses `/* */`. Templates: `KOTLIN_SHOULD_T` (`%FUNC%`/`%CONTEXT%`/`%BRANCHES%`), `KOTLIN_SHOULD_BRANCH_T` (`%ABOUT%`/`%CONDITION%`/`%REACTION%`/`%FIELD%`), `KOTLIN_SHOULD_RESET` ("ShouldReset"). (`KOTLIN_SHOULD_INDENTATION` = `"        "` is defined in `kotlinConst.swift` but no longer referenced — dead since the indentation formatter was removed.)
- **Adding an `out*` section needs THREE things, not one**: the codegen fun + templates, the should in `dialect.yml`, AND the YML→Kotlin bridge for whatever field the should keys on. `outStructs` keys on `entityFieldTypes`, so without `entityFieldTypes: kotlinSet(...)` **and** `entityTypes: kotlinSet(...)` the should can never fire — the `KotlinContext` fields simply stay empty and `outStructs` silently stays `""` with no error anywhere. Check the regenerated `dialect.swift` contains the new `kotlinSet(F.<field>, c.<field>)` lines inside `ymlRegisterEffects`. Two Kotlin lambda traps bite at the compile-verify step (both reproduced standalone against `kotlinc` 2.3.10, K2 frontend): a single-parenthesised lambda param `{ (c: T) -> }` is a **destructuring declaration**, not a one-param lambda, so it fails with `cannot infer type for implicit value parameter 'it'` plus a flood of `component1() is ambiguous` candidates — and the `{ x in ... }` implicit-param shorthand is rejected outright with `unresolved reference 'x'`. Always write `{ c: T -> ... }` / `{ f -> ... }` with explicit `->`.
- **Kotlin `out` (final concatenation)**: `KotlinContext.out` = `KOTLIN_OGS_PKG + "\n" + otherBase64ToString(KOTLIN_EMB64_CORE).replacingOccurrences(of: KOTLIN_OGS_PKG, with: "") + c.outFields + c.outStructs + c.outContexts + c.outSets + c.outShoulds + c.outRegisterShoulds + c.outRegisterEffects` — package line, then the embedded Kotlin core (package line stripped), then `object F`, then the structs, then the contexts, then the Set funcs, then the should funcs, then the RegisterShoulds funcs, then the RegisterEffects funcs last. The order mirrors the Swift `out` exactly. Produced by the `out` should when `c.recentField == F.outRegisterEffects` (the very last section to populate). The `out` should also declares `path` resolved from `outputPaths` matching `KOTLIN_TYPE`.
- **Kotlin `outRegisterShoulds` (parallel to the Swift one)**: `KotlinContext.outRegisterShoulds` holds the generated `<component-prefix>RegisterShoulds()` function text, produced by the `outRegisterShoulds` should: when `c.recentField == F.entityShoulds`, `c.outRegisterShoulds = kotlinRegisterShoulds(c.entities, c.entityShoulds)` and `recentField` becomes `F.outRegisterShoulds`. Appended after `outShoulds`. `kotlinRegisterShoulds`/`kotlinRegisterShould` (2 params: `entities [String]`, `entityShoulds [Int:[String]]`) mirror the Swift pair exactly — same `entityShoulds.keys.sorted()` collection, same func name `prefix + KOTLIN_REGISTER_SHOULDS_SUFFIX`, same should-func name `prefix + KOTLIN_SHOULD_RESET + otherCapitalize(should)`. Templates: `KOTLIN_REGISTER_SHOULDS_T` (`%FUNC%`/`%CONTEXT%`/`%ITEMS%`), `KOTLIN_REGISTER_SHOULDS_ITEM_T` (`%SHOULD%`), `KOTLIN_REGISTER_SHOULDS_SUFFIX` ("RegisterShoulds"). Three deliberate Kotlin deviations from the Swift body: (1) the items are `::shouldFunc` **function references**, not bare function names — Kotlin has no implicit reference syntax, so the bare-name Swift list becomes a `listOf(...)` of `::name`s; (2) the cast is `f(c as <Context>)`, a plain downcast, so it needs no `as!`; (3) lambda params use `{ f -> ... }` / `{ c -> ... }` with an explicit `->` because **this project's `kotlinc` (2.3.10, K2 frontend) rejects the `{ x in ... }` implicit-parameter shorthand outright** — it reports `unresolved reference 'x'`. The shoulds it registers are the real transpiled ones described in Kotlin `outShoulds`.
- **Kotlin `outRegisterEffects` (parallel to the Swift one)**: `KotlinContext.outRegisterEffects` holds the generated `<component-prefix>RegisterEffects()` function text, produced by the `outRegisterEffects` should: when `c.recentField == F.transpiledOneliners`, `c.outRegisterEffects = kotlinRegisterEffects(c.entities, c.transpiledOneliners)` and `recentField` becomes `F.outRegisterEffects`. Appended last in `KotlinContext.out`. `kotlinRegisterEffects`/`kotlinRegisterEffect` (2 params: `entities [String]`, `entityOneliners [Int:[Oneliner]]`) mirror the Swift pair — same `entityOneliners.keys.sorted()` collection, same non-empty filter, same func name `prefix + KOTLIN_REGISTER_EFFECTS_SUFFIX` — but the `outRegisterEffects` should keys on the TRANSPILED oneliners (`F.transpiledOneliners`, populated by the Conv pipeline), so the registered reactions are real Kotlin, not no-ops. Templates: `KOTLIN_REGISTER_EFFECTS_T` (`%FUNC%`/`%ITEMS%`), `KOTLIN_REGISTER_EFFECT_ITEM_T` (`%CONTEXT%`/`%FIELD%`/`%REACTION%`), `KOTLIN_REGISTER_EFFECTS_SUFFIX` ("RegisterEffects"). Three Kotlin-specific differences: (1) **no `let _: <Context>? =` type pin** — Swift needs it to infer the generic `T` in `registerOneliners<T>`; the Kotlin core's `registerOneliners(ctrl: DialectController, items: Array<Any>)` is not generic, so the `let _ =` trick does not exist and simply calling it is correct; (2) the item is `F.%FIELD%, { c: %CONTEXT% -> %REACTION% },` — the param is **unparenthesized** and typed as the CONCRETE context (`RootContext`), because a parenthesized single param `{ (c: T) -> }` is parsed as a **destructuring declaration** and fails with `cannot infer type for implicit value parameter 'it'` (the `{ x in ... }` shorthand is also rejected outright); `registerOneliners` casting the callback to `(c: DialectContext) -> Unit` still accepts the concrete-typed lambda because JVM generic erasure makes both erasures the same `Function1`; (3) the reaction is the real transpiled Kotlin (`print(c.countText)`, `RootVM.shared!!.countText = c.countText`, `otherWriteFile(c.path, c.out)`) emitted verbatim via `kotlinFormatCode([oneliner.reaction])` — no `if (false)`/`/** */` wrapper. Note `transpiledOneliners` needs a Kotlin bridge to be reachable at all — see the YML→Kotlin bridges / Conv bullets.
- **YML→Kotlin bridges**: `YMLComponent` feeds Kotlin with oneliners `entities: kotlinSet(F.entities, c.entities)` (drives `outSets`), `entityFields: kotlinSet(F.entityFields, c.entityFields)` (drives `outFields`), `entityFieldTypes: kotlinSet(F.entityFieldTypes, c.entityFieldTypes)` + `entityTypes: kotlinSet(F.entityTypes, c.entityTypes)` (both drive `outStructs`), `entityShoulds: kotlinSet(F.entityShoulds, c.entityShoulds)` (drives `outRegisterShoulds`) and `outputPaths: kotlinSet(F.outputPaths, c.outputPaths)` (drives `KotlinContext.path`). It ALSO carries the `convSet` bridges `entityOneliners: convSet(F.entityOneliners, c.entityOneliners)` and `entityShouldBranches: convSet(F.entityShouldBranches, c.entityShouldBranches)`, which feed the Conv pipeline; the `kotlinSet`/`swiftSet` twins of those two still exist, but Kotlin no longer keys `out*` on the raw fields. The fields Kotlin's `out*` sections key on are now the TRANSPILED ones — `outShoulds`←`F.transpiledShouldBranches`, `outRegisterEffects`←`F.transpiledOneliners` — and those are pushed into `KotlinContext` by the Conv component's own oneliners (`transpiledOneliners: kotlinSet(...)`, `transpiledShouldBranches: kotlinSet(...)`), NOT by YML. In the oneliners list each `kotlinSet(...)` line sits immediately BEFORE its `swiftSet(...)` twin so the two ports stay paired.
- **Conv pipeline (queue-based Swift→Kotlin transpilation)**: the generator's `ConvComponent` walks every should-branch condition/reaction and every oneliner reaction through the LLM one snippet at a time, then rebuilds the transpiled data the Kotlin codegen consumes. `components/conv/convFun.swift` holds the pure helpers (`convQueuePrompt`, `convSrcQueueShoulds`, `convSrcQueueOneliners`, `convTranspiledShouldBranch(es)`, `convTranspiledOneliner(s)`); the `ConvComponent` is a hand-written `class` in `components/conv/conv.swift` (symlinked into BOTH `generator/ver-mac/src/conv/` — which needs `convFun.swift` — and `transpiler/ver-mac/src/conv/`, which has only `conv.swift`/`convConst.swift`). Flow is driven entirely by `ConvContext.recentField` shoulds in `generator/dialect.yml`: YML bridges `entityShouldBranches`/`entityOneliners` in via `convSet` → `isConvertingShoulds` true → `srcQueue = convSrcQueueShoulds(entityShouldBranches)` (two items per branch, condition then reaction, in `keys.sorted()` order) → `srcId = 0` → `prompt = convQueuePrompt(srcQueue, srcId)` = `CONV_PROMPT_PREFIX + CONV_PREFIX_SWIFT + id + "\n" + item + CONV_PROMPT_SUFFIX` → `llmLoad` → each reply appended to `dstQueue`, `srcId += 1`, until `dstQueue.count == srcQueue.count` → `isConvertingShoulds` false → `transpiledShouldBranches = convTranspiledShouldBranches(entityShouldBranches, dstQueue)` (per snippet, drops the model's echoed `KOTLIN-<id>` first line if present, keeps the rest verbatim). `transpiledShouldBranches` then flips `isConvertingOneliners` true and the SAME machinery reruns for oneliners (`convSrcQueueOneliners` = one reaction per oneliner → `transpiledOneliners = convTranspiledOneliners(entityOneliners, dstQueue)`). Both results publish to `KotlinContext` via `kotlinSet`, which is what makes `outShoulds`/`outRegisterEffects` emit real Kotlin — so a generator run LLM-transpiles the example before writing `dialect.kt`. Sequencing is load-bearing: shoulds MUST finish before oneliners start (`isConvertingOneliners`'s branch 1 keys on `F.transpiledShouldBranches`), because both phases reuse `dstQueue`/`srcId`/`srcQueue`.
- **Android port (example/ver-android)**: a syntactic Compose mirror of the Swift example, not a port of the *engine* — the engine still comes from the generated `dialect.kt` (embedded `KOTLIN_EMB64_CORE` + `object F` + `rootSet`). `rootVM.kt` is `object RootVM { var countText by mutableStateOf(""); var shared: RootVM? = this; private set }`: Swift's `ObservableObject` + `@Published` becomes `mutableStateOf` behind a `by` delegate, and Swift's `static private(set) weak var shared: RootVM?` is **mirrored, not dropped** — because `RootVM` is an `object`, `shared` just self-references (`var shared: RootVM? = this` with `private set`), so `RootVM.shared` is the same instance `RootVM` already is. Both access styles therefore resolve: `RootVM.countText` (the view) and `RootVM.shared!!.countText` (the generated `rootRegisterEffects` reaction). `RootView()` still takes no VM param (unlike Swift's `RootView(_ vm: RootVM)`). Both component files declare the FLAT `package org.opengamestudio` (same as the generated `dialect.kt`) rather than dir-matching `org.opengamestudio.root[.view]` — that keeps `RootVM`, `RootView` and `rootSet` resolvable with **zero imports**, mirroring Swift's single-module access. `components/root/android/root.kt` is a hand-written `object RootComponent { val ctrl = DialectController(RootContext()); init { rootRegisterEffects(ctrl); rootRegisterShoulds(ctrl) }; fun setup() { rootSet(F.didSetup, true) } }` — an `object`, NOT a generated class with a `singleton`, which is why `KOTLIN_SET_T` can now emit a live `%COMPONENT%.ctrl.set(key, value)` body. The generated `RootContext` (`count: Int`, `countText: String`, `didClickIncrement: Boolean`, `didLaunch: Boolean`, `didSetup: Boolean`) arrives via `outContexts` with `Bool` already mapped to `Boolean`, and `rootRegisterShoulds`/`rootRegisterEffects` arrive alongside it. `MainActivity.kt` WIRES IT UP: `otherSetupConsoleLogging(root.ctrl, "Root")` then `root.setup()`, and `RootView.kt`'s Button calls `rootSet(F.didClickIncrement, true)`. **The engine loop genuinely runs AND the counter moves**, because the should *bodies* and effect *reactions* are now REAL transpiled Kotlin (the generator's Conv pipeline LLM-transpiles both; see the Conv bullet): `rootShouldResetCount` does `c.count += 1`, `rootShouldResetCountText` does `c.countText = "Count: '${c.count}'"`, and the effect is literally `F.countText, { c: RootContext -> RootVM.shared!!.countText = c.countText },`. The `!!` and the `RootVM.shared` access are why `shared` exists (above), and the callback is typed as the concrete `RootContext`, so no `(c as RootContext)` cast is involved.
- **`outRegisterShoulds` (v4-specific, parallel to `outSets`/`outShoulds`)**: `SwiftContext.outRegisterShoulds` holds the generated *`<component-prefix>RegisterShoulds()` function text* (e.g. `cliRegisterShoulds`/`swiftRegisterShoulds`/`ymlRegisterShoulds`/`rootRegisterShoulds`), produced by the `outRegisterShoulds` should: when `c.recentField == F.entityShoulds`, `c.outRegisterShoulds = swiftRegisterShoulds(c.entities, c.entityShoulds)` and `recentField` becomes `F.outRegisterShoulds`. Concatenated into `out` AFTER `outShoulds`, so RegisterShoulds funcs ARE generated into `dialect.swift` and must NOT be hand-written in tmp anymore (components call the generated register funcs directly). `swiftRegisterShoulds` (in `components/swift/swiftFun.swift`, 2 params: `entities [String]`, `entityShoulds [Int:[String]]`) collects entity ids via `entityShoulds.keys.sorted()`, then for each component calls `swiftRegisterShould(contextName, shoulds)` which emits a `func <prefix>RegisterShoulds(_ ctrl: DialectController)` registering `prefix + SWIFT_SHOULD_RESET + otherCapitalize(should)` per should. Templates: `SWIFT_REGISTER_SHOULDS_T` (`%FUNC%`/`%CONTEXT%`/`%ITEMS%`), `SWIFT_REGISTER_SHOULDS_SUFFIX` ("RegisterShoulds"). NOTE: overload resolution separates the codegen `swiftRegisterShoulds(entities, entityShoulds) -> String` from the generated `func swiftRegisterShoulds(_ ctrl: DialectController)` — same pattern as `swiftSet` codegen vs generated Set funcs.
- **`outRegisterEffects` (v4-specific, parallel to `outRegisterShoulds`)**: `SwiftContext.outRegisterEffects` holds the generated *`<component-prefix>RegisterEffects()` function text* (e.g. `cliRegisterEffects`/`swiftRegisterEffects`/`ymlRegisterEffects`/`rootRegisterEffects`), produced by the `outRegisterEffects` should: when `c.recentField == F.entityOneliners`, `c.outRegisterEffects = swiftRegisterEffects(c.entities, c.entityOneliners)` and `recentField` becomes `F.outRegisterEffects`. Concatenated into `out` AFTER `outRegisterShoulds` (very last section), so RegisterEffects funcs ARE generated into `dialect.swift` too — ALL oneliner/effect/bridge registration is generated (`tmp.dialect.swift` was removed). `swiftRegisterEffects` (in `components/swift/swiftFun.swift`, 2 params: `entities [String]`, `entityOneliners [Int:[Oneliner]]`) collects entity ids with non-empty oneliners via `entityOneliners.keys.sorted()`, then for each component calls `swiftRegisterEffect(contextName, oneliners)` which emits a `func <prefix>RegisterEffects(_ ctrl: DialectController)` body `let _: <Context>? = registerOneliners(ctrl, [...] )` with one item `F.<field>, { (c: <Context>) in <reaction> },` per Oneliner (reaction used verbatim from yml). Templates: `SWIFT_REGISTER_EFFECTS_T` (`%FUNC%`/`%CONTEXT%`/`%ITEMS%`), `SWIFT_REGISTER_EFFECTS_SUFFIX` ("RegisterEffects"). NOTE: overload resolution separates the codegen `swiftRegisterEffects(entities, entityOneliners) -> String` from the generated `func swiftRegisterEffects(_ ctrl: DialectController)` — same pattern as `swiftRegisterShoulds`/`swiftSet`.
- **`out` (final concatenation)**: `SwiftContext.out` = `otherBase64ToString(SWIFT_EMB64_CORE) + c.outFields + c.outStructs + c.outContexts + c.outSets + c.outShoulds + c.outRegisterShoulds + c.outRegisterEffects`. This ordering (GENERATED core first, then F, structs, contexts, Set funcs, should funcs, RegisterShoulds funcs, then RegisterEffects funcs last) means ALL target code is fully generated — `ver-mac/src/dialect.swift` is the only generator source file. The `out` should also declares `path` (Swift output path) resolved from `outputPaths` matching `SWIFT_TYPE`.
- **CHICKEN-EGG / struct F upkeep (critical)**: `F` (`struct F { static let ... = "<name>" }`) is a field-name constant struct. It is defined ONLY in the **generated** `ver-mac/src/dialect.swift` (`struct F` is generated via `swiftFields`/`outFields`; nothing references `F.*` before `dialect.swift` compiles). `dialect.swift` cannot be regenerated in strict purity (regen needs the built generator, which needs dialect.swift). So **whenever dialect.yml adds a new field to any context, you MUST hand-patch the new `static let <field> = "<field>"` into the generated `ver-mac/src/dialect.swift` struct `F`**, placed in ASCII-alphabetical order between its siblings (e.g. `outStructs` goes between `outFields` and `outputPaths` — `S`(0x53) < `p`(0x70)). Skip this and the build fails (`F.outStructs` unresolved). This hand-patch is exactly what a future regen would emit, so it stays consistent. The generated **should funcs** (which live in `dialect.swift` via `outShoulds`) also reference `F.*` — hand-patching `F` keeps those self-consistent at build/run.
- **Chicken-egg checklist (when SSOT dialect.yml gains a field on a context — e.g. `entityFieldTypes` + `outStructs` on SwiftContext)**: (1) hand-patch the `static let <field> = "<field>"` into the generated `ver-mac/src/dialect.swift` struct `F`, alphabetically; (2) if another component's oneliner should feed it (YML→Swift bridge), add its oneliner in `dialect.yml` (e.g. `entityFieldTypes: swiftSet(F.entityFieldTypes, c.entityFieldTypes)` — this both feeds `SwiftContext.entityFieldTypes` and, via `recentField`, triggers the generated `swiftShouldResetOutStructs`); the bridge regenerates into `ymlRegisterEffects` via `outRegisterEffects` (regen-stability: build → regen → verify byte-identical, update hash). Context struct vars, `field<T>`/`setField` branches, should funcs, Set funcs, and RegisterShoulds/RegisterEffects funcs are NO LONGER hand-written — they regenerate via `swiftContexts`/`outContexts`, `swiftShoulds`/`outShoulds`, `swiftSets`/`outSets`, `swiftRegisterShoulds`/`outRegisterShoulds`, `swiftRegisterEffects`/`outRegisterEffects`.
- **Per-component helper files** (components/yml/): `ymlConst.swift` (global constants like `YML_PREFIX_VERSION`), `ymlFun.swift` (pure helpers/parsers like `ymlParseVersion`), `ymlEffect.swift` (effects that `ymlSet` results back), `ymlAux.swift` (aux/print helpers). Matching `cliConst/cliFun/cliEffect/cliAux`.
- **YML schema parsing** (chunks): input is split into **chunks** = `[String: [String]]` keyed by the chunk's first (non-indented) line. Blank lines (`""`) delimit chunks — detected by `ymlIsLineChunkStart`/`ymlIsLineChunkEnd`. Downstream parsers consume structures: `ymlParseEntities` (top-level `Key:` lines, `hasSuffix(":")`), `ymlParseEntityTypes` (indented `type:` under each entity, `YML_PREFIX_TYPE` bakes in the 4-space indent), `ymlParseVersion` (from the chunk key prefix `YML_PREFIX_VERSION`). Should-chains cascade: `inputLines` → `chunks`/`entities`, then `chunks` → `version`, `entities` → `entityTypes`.
- **ShouldBranch struct (renamed fields)**: dialect.yml's `ShouldBranch` struct entity has fields `about` (String), `condition` ([String]), `reaction` ([String]) — these were **renamed** from `desc`/`if`/`then` to avoid the Swift keywords `if`/`then` and match "condition/reaction" semantics. The YAML **input** markers for parsing still read `if:`/`then:` (prefixed lines), but they map into `condition`/`reaction` fields via `isParsingCondition`/`isParsingReaction` flags in `ymlParseEntityShouldBranches`. Generated code: `struct ShouldBranch` (plain struct, in `outStructs`) + the `F.about/condition/reaction` constants (hand-patched into the generated `dialect.swift`).
- **Rename propagation (single SSOT in dialect.yml)**: when a struct *field* is renamed in dialect.yml (like `desc/if/then` → `about/condition/reaction`), update ALL of these in one pass: (1) the `ShouldBranch` struct declaration + `F` constants in the generated `ver-mac/src/dialect.swift` (hand-patch); (2) `ymlFun.swift` — field writes (`.about`), local var names, parser flags (`isParsingCondition`/`isParsingReaction`) and their comments; (3) `swiftConst.swift` `SWIFT_SHOULD_BRANCH_T` template placeholders (`%ABOUT%`/`%CONDITION%`/`%REACTION%`); (4) `swiftFun.swift` commented `swiftShould` refs (`branch.about`, `.condition`, `.reaction`); (5) C `core/c/dialect.h` `ShouldBranch` struct (`about`/`condition`/`reaction`; the `if`→`condition` change also *removes* the old `if_` C-keyword workaround). After the rename, verify regen-stability: run `util/run-c-test`, `util/build-generator`, then `util/run-generator --file=dialect.yml` and confirm `ver-mac/src/dialect.swift` regenerates byte-identical to the hand-patch (hash matches).
- **Keyword collision conventions across ports**: Swift backticks Swift keywords (`` `if` ``, `` `type` ``); C appends `_` (former `if_`). Renaming a field away from a keyword lets you drop the escape in every port. The `if`/`then` in `ymlConst.swift` prefix constants (`YML_PREFIX_SHOULD_BRANCH_IF` = `"                if:"`, then-marker) are the *input syntax*, NOT struct fields — they intentionally keep the `if:`/`then:` spelling and are NOT part of the rename.

## Swift gotchas (learned the hard way)

- `!x.isEmpty()` parses as force-unwrap — use `!x.isEmpty` or `x != ""`.
- `String.startsWith(prefix)` is not Swift — use `hasPrefix`.
- `String.substring(from:)` is not Swift — use `dropFirst(n)`/`dropFirst(prefix.count)`.
- `String.trim()`, `find`, `indexOf`, `trimming` do NOT exist here — use `hasPrefix`/`hasSuffix`/`isEmpty`/`contains`. To strip indentation, either bake it into the `YML_PREFIX_*` constant (e.g. `"    type: "`) or loop `while s.hasPrefix(" ") { s = String(s.dropFirst(1)) }`.
- `String.split(separator:)` DEFAULTS to `omittingEmptySubsequences: true` — blank lines get silently dropped. Pass `omittingEmptySubsequences: false` when blank lines matter (chunk boundaries depend on them!).
- `Substring` is NOT implicitly convertible to `String` — `s.dropFirst(1)`/`dropLast(1)` return `Substring`; you must write `String(...)` explicitly (at assignment, `.append`, and argument boundaries).
- `[String] += someString` fails (String is treated as a character Sequence) — use `.append(someString)`.
- Kotlin-style `if cond && let x = ...` is invalid Swift — use a comma: `if cond, let x = ...`.
- `str.split("\n")` is wrong — use `str.split(separator: "\n")`. But for chunking you need the empty-subsequences variant above.
- Optionals at the boundary: `value as! Bool`/`as! String` force-casts in setField; a String field wrote from an effect must match its declared type exactly.

## Generator gotchas (learned the hard way)

- **Swift multiline-string template spacing is subtle**: the newline immediately before the closing `"""` is stripped, and only the newline right after the opening `"""` is consumed. So a template written `%ITEMS%}` ends with NO trailing newline, and the next section's single leading newline yields NO blank line between them (the generated Kotlin came out as `}\nfun cliSet(`). Mirror the `SWIFT_*_T` shapes exactly — `%ITEMS%` alone on its line, `}` on the next line, one blank line before the closing `"""` — and verify the separator with `repr()` on a slice of `/tmp/dialect.log` rather than by eye.
- **A new bridge oneliner needs TWO build+regen cycles**: the oneliner only exists in the generated `dialect.swift`, so the binary built from the *previous* `dialect.swift` does not have it yet. Correct sequence: `util/build-generator` -> `run-generator` -> `util/build-generator` -> `run-generator`, then confirm the hash is stable across one more cycle.
- **Run the generator from `generator/`**: `util/run-generator` resolves `dialect.yml` relative to the cwd, so from the repo root it fails with "Could not read file" (and still exits 0 after writing core-only artifacts).
- **`/tmp/dialect.log` is the inspection surface**: `util/step/runGenerator` hardcodes the generator's stderr there, and `otherSetupConsoleLogging` prints every field as `ИГР <Component> k/v: '<field>'/'<value>'`. That log is the ONLY way to see a log-only output such as the Kotlin `out` (the generator's own `dialect.yml` has no `type: kotlin` target, so nothing is written to disk).
- **`otherWriteFile` fails silently**: it is `try? content.write(toFile:)`, so an empty path (no matching `output:` entry) or a missing parent directory means the file is never written and the run still exits 0. Always confirm the `ИГР otherWF path/content.count:` line shows a non-empty path AND a plausible char count.
- **Compile-verify the log-only Kotlin output**: nothing writes the generator's Kotlin `out` to disk, so nothing else would catch invalid emitted Kotlin (e.g. a wrong type spelling). Extract the `ИГР Kotlin k/v: 'out'/'…'` record from `/tmp/dialect.log` — skip the value's OWN quotes as well as the field's, the payload spans many physical lines — write it to a `.kt` file and run `"/Applications/Android Studio.app/Contents/plugins/Kotlin/kotlinc/bin/kotlinc" File.kt -d out` with `JAVA_HOME` at Android Studio's JBR. To unit-test a pure codegen fun WITHOUT a regen cycle, compile its `components/*/*.swift` pair with a throwaway `main.swift` (they only reference the file's own constants).

## Agent gotchas (learned the hard way)

- **`otherLaunch()` (= `RunLoop.current.run()`, in shared `components/other/other.swift`) is load-bearing.** `llmLoad` is fully async (`URLSession.dataTask(...).resume()`, no `DispatchSemaphore`), so without a running run loop `main` returns, the process exits, and the callback never fires — you get silence, not an error. The process now DOES auto-exit, but only after a reply arrives: `AgentComponent`'s `willShutdown` should sets `willShutdown = true` on `F.reply`, and the `willShutdown: otherShutdown()` oneliner calls `exit(0)`. A run that never gets a reply (no Ollama, hung server) still parks forever and must be killed (Ctrl-C => exit 130, or SIGTERM), because there is no timeout.
- **THE REPLY-PRINTS-BEFORE-EXIT ORDERING IS AN ACCIDENT OF ALPHABETICAL REGISTRATION, NOT A GUARANTEE.** Both `AgentComponent` shoulds (`consoleOutput` and `willShutdown`) fire on the same `F.reply`, and `executeFunctions` appends them to the queue in *registration* order, so whichever registers first is applied first. `agentRegisterShoulds` happens to list `consoleOutput` before `willShutdown` (ASCII order), so the reply prints and only then does `exit(0)` fire. Rename either field and the order can flip — `willShutdown` first would `exit(0)` before the reply was ever printed, and you would get a silent, empty run. When adding an output field alongside `willShutdown`, re-verify the printed output actually appears rather than trusting the naming.
- **`exit(0)` is the ONLY way to end this process — `CFRunLoopStop` does not work.** `RunLoop.run()` is a `while true` loop, so `CFRunLoopStop(CFRunLoopGetMain())` is consumed by the current iteration and the loop simply re-enters: measured, it never returned and the process hung indefinitely (killed after 30 min), from BOTH a background thread and from main. There is no graceful stop short of `exit()`.
- **`exit(0)` MUST NOT be called from the `netLoad` callback thread, because `llmSetAsync` is always deferred.** Calling `exit(0)` right after `llmSetAsync` queues the write and races the main queue: with main idle the write usually survives (libdispatch drains the main queue during `exit()` teardown, so it lands *after* `exit()` was entered — teardown luck, not ordering), but with main BUSY (mid-cascade, or any main-thread work) the queued write is destroyed outright and the response is silently lost with nothing logged. `otherShutdown` is safe precisely because it runs as an oneliner effect ON MAIN, inside `llmSet`'s synchronous cascade, after the write and after every downstream effect.
- **`llmExtractReply` hand-parses the envelope with split/substring only — no `JSONSerialization`.** Deliberate, so it stays a pure string fun with no Foundation dependency. Algorithm: `components(separatedBy: LLM_LINE_DELIMITER)` (= `","`), take the segment with `hasPrefix(LLM_REPLY_PREFIX)` (=`response":"`, so a look-alike key such as `"responses"` cannot match), drop the prefix (the value's own trailing `"` is swallowed by the delimiter), then run `llmUnescape` on what is left. `","` is the boundary BETWEEN keys and never occurs inside a value, so a reply holding a comma (`Apples, Bananas`) survives whole, where a plain `,` split cut it after `Apples` and needed the segments re-joining. **KNOWN LIMIT: `","` only appears between two STRING values**, so if the key before `response` holds a non-string the segment is glued (`done":true,"response":"last`) and `hasPrefix` misses it — and so does `response` being the FIRST key, because nothing separates it from the opening `{`. Either way the fun returns `"ERROR Could not parse response"` (not `""`). Ollama's own payload is safe because `created_at` (a string) always precedes `response`; splitting on `,"` (comma-quote) instead would match every key boundary and remove the limit at no extra cost. Reading a raw Ollama reply WITHOUT `llmUnescape` leaves `\n`, `\"` and `\u0026` as literal backslash sequences — that is how the transpiler first printed its whole transpiled output as one line.
- **`llmUnescape` decodes JSON string escapes in ONE left-to-right pass** (`components/llm/llmFun.swift`), added when the transpiler began printing LLM replies: the extracted value still carries the JSON encoding, so it printed `KOTLIN-1\n  c.count += 1` literally. Single pass is load-bearing — a naive `replacingOccurrences(of: "\\n")` over `\n` would first turn an escaped backslash into a real newline. Handles `\" \\ \/ \b \f \n \r \t` and `\uXXXX`, including surrogate pairs (`\uD83D\uDE00` → 😀). Anything it cannot decode — unpaired surrogate, bad or truncated hex, unknown escape, trailing backslash — is emitted VERBATIM rather than dropped, so nothing is silently lost. Pure string fun, no `JSONSerialization`.
- **`llmSetAsync` is ALWAYS deferred — do not add a main-thread fast path to it.** `DispatchQueue.main.sync` from the main thread DEADLOCKS, so it was briefly called `llmSetSync` and briefly carried an `if Thread.isMainThread { llmSet(...) }` fast path. Neither is needed: `netLoad` funnels EVERY outcome (including its invalid-URL guard, which runs on the caller's thread) through the same `reportSuccess` / `reportError` callbacks, so `llmSetAsync` stays the single owner of the main-queue hop with no special cases. The trade-off is that "request finished => state updated" is NOT guaranteed — verified consequence: a malformed URL now lands in `responseError` one main-queue turn AFTER `llmLoad` returns, instead of synchronously.
- **`netLoad` knows nothing about Dialect, which is the whole point of the split.** It reports through two callbacks taking a `NetResponse` rather than calling `llmSet`, so it has no field keys and no context. If you find yourself adding an `LLM_*` reference to `net/`, the boundary has leaked.
- **A real Ollama may already own port 11434.** A "connection refused" test server can silently lose the race to a running `ollama serve`; check before assuming the stub is answering. Real answers are `{"models":[...]}` from `GET /api/tags`.
- **No request timeout.** `LLM_DEFAULT_TIMEOUT` was removed along with the semaphore, so a hung server keeps the agent parked forever and looks identical to a healthy idle one. `URLSessionConfiguration.timeoutIntervalForRequest` is the non-blocking way to bound it if that distinction ever matters.
- **A non-2XX status routes to `responseError`, but the status is NOT a field.** `netLoad`'s callback captures `response` and tests `!(200 ..< 300).contains(http.statusCode)`, so a 404 no longer masquerades as success — `contents` becomes `"<status> <body>"` (e.g. `404 {"error":"model 'x' not found"}`), the body being the real diagnosis. It is ALWAYS both halves, with no fallback for an empty body, so a bodyless `503` yields `"503 "` — status, space, then nothing. `NetResponse` still has only `contents`/`req`, so branching on status programmatically means string-matching `contents`; add a field to the struct in agent/dialect.yml (then the regen cycle) if you ever need it.
- **The Ollama tag must be exact and lowercase, and `/api/tags` is the only way to see what you have.** The bare `qwen2.5-coder` returns 404, and Ollama outright rejects the capitalized HuggingFace spelling (`Qwen2.5-Coder-1.5B`); only `qwen2.5-coder:1.5b` (lowercase) resolves, so `LLM_DEFAULT_MODEL` carries that tag. The 1.5b is the transpiler default: 986 MB disk / 1.16 GB VRAM, byte-perfect 20/20 + mean 14.4 s/run on the 26-block ref/sample.swift (1275 in / 1322 out chars, 1 unique output over 20 runs). `qwen2.5-coder:0.5b` (397 MB / 479 MB VRAM, ~3.9 s/run) is ONLY a copy-task fallback: probing `/tmp/gen-suite.swift` showed 0.5b fails every transform the moment the input leaves the example-covered content, so it is NOT the default. `qwen2.5-coder:3b` (2.16 GB VRAM, ~13.3 s/run), `qwen2.5-coder:7b` and `phi4-mini:3.8b` are also pulled. A "never touched Ollama" box is not necessarily model-less — `curl :11434/api/tags` lists everything already pulled, `run` only downloads weights.
- **LLM transforms on novel input are example-anchored, and only word-level rewrites generalize.** Measured with `/tmp/gen-suite2.swift` (8 blocks of never-seen identifiers — `c.title`/`c.rows`/`store.proxy!` — probing every glossary rule) on `qwen2.5-coder:1.5b`: pass-throughs are always correct (new field names, `!=`, `>=`, `&&`, assignments, `let`→`val`); interpolation, `listOf()`, lambda `->`, `isEmpty()` and ternary generalize once each has its own glossary pair (interpolation needed a SECOND example on a second field to break the `count`-anchoring) plus its rule; but the single-char deviations (`as!`→`as`, `x!`→`x!!`) NEVER fire on novel content — they only apply when the input line matches an example pair almost exactly, because token-level copy bias wins. Current probe score: 6/8, the 2 failures being exactly the novel single-char blocks. Practical rule: give every word-level transform its own example pair (mirroring proto-transpile's `extraRules`); treat single-char transforms as copy-task-only.
- **Glossary ordering rule: transforms first, pass-throughs last — the tail of a long input is copied verbatim.** The model rewrites reliably in the head of a long input and degrades to copying past roughly 70% of it. Measured: with the two single-char blocks at positions 18/21 of a 23-block sample the run scored 21/23 (both copied verbatim); moving them to positions 1-2 flipped both to correct at 23-block length, and packing ALL five single-char transform blocks into positions 1-5 with the 14 pass-through blocks filling the tail is what makes the 20-run battery 20/20 byte-perfect. A transform block placed late gets copied instead of rewritten (invalid Kotlin slips out silently); a pass-through block placed late is copied, which is already the right answer — so the tail must consist only of pass-throughs.
- **`stream:false` means total silence for the whole generation, and it is unbounded.** Measured ~6s for a 150-word answer with nothing logged, because the server holds the connection until generation completes. `stream:true` does NOT fix that on its own — `URLSession.dataTask` still invokes its completion handler only ONCE, at the end (measured: 10s of silence, then a single 23KB dump of 209 newline-separated chunks). Incremental delivery needs `URLSessionDataDelegate.urlSession(_:dataTask:didReceive:)`, which showed a first chunk at ~180ms over 6.6s. With no timeout installed, "slow generation" and "hung server" are indistinguishable at the terminal.
- **`llmBody` JSON-encodes instead of interpolating, and sends `options` = `seed`(42) + `temperature`(0.0) + `top_k`(1).** `LLM_TOP_K = 1` is TRUE greedy decoding and is what actually pins output determinism — `seed`+`temperature: 0.0` ALONE does NOT determinize `qwen2.5-coder:1.5b` (measured 7 different outputs over 20 identical transpiler runs, curl-verified the same). With `top_k: 1` the transpiler measured byte-identical 20/20 on ref/sample.swift. Because `llmBody` is shared, `agent/` replies are also greedy/deterministic. A prompt containing `"`, `\` or a newline would corrupt a hand-built `{"prompt":"..."}` literal; `JSONSerialization` is what makes `--prompt='say "hi"'` safe.
- **Smoke-test the built binary, not just a stubbed harness.** `util/build-agent` compiles cleanly long before the wiring is correct; `agent/ver-mac/.build/release/agent --prompt="hi"` in the background, `sleep 3`, confirm still alive + `ИГР LLM k/v: 'response'` present, then SIGTERM, is the only end-to-end check that exercises CLI parse -> oneliner -> async load -> main-queue push -> cascade.
- **Cloning a target usually needs a NEW constant in the shared component, not a renamed one.** `components/cli/cliConst.swift` is SHARED — `agent/` and `transpiler/` symlink the SAME `components/cli/`. A blind `agent`->`transpiler` sweep over a target's `dialect.yml` rewrites `CLI_CONSOLE_USAGE_AGENT` into `CLI_CONSOLE_USAGE_TRANSPILER`, which the build cannot resolve (`cannot find 'CLI_CONSOLE_USAGE_TRANSPILER'` at the yml reaction site) unless you also DEFINE it. Resolved by adding `CLI_CONSOLE_USAGE_TRANSPILER` as a sibling with its own text (`transpiler --file=/path/to/file.swift`), so each target names itself while the source stays shared. So: rename only the target's OWN symbols (`TranspilerComponent`/`TranspilerContext`, `transpilerSet`, `transpilerShouldReset*`, `transpilerRegister*`); for a shared symbol, add a sibling constant rather than reusing or renaming an existing one.
- **CLI console output interrupts the target — a no-args run prints usage and exits instead of hanging.** Same mechanism in `agent/` and `transpiler/`: `CLIComponent` gains the oneliner `- consoleOutput: <prefix>Set(F.cliDidConsoleOutput, true)`, bridging into the target's OWN context (`AgentContext`/`TranspilerContext` field `cliDidConsoleOutput: Bool`), and the target's `willShutdown` should gains a second branch on `c.recentField == F.cliDidConsoleOutput` -> `c.willShutdown = true`, whose `willShutdown: <prefix>Shutdown()` oneliner is `exit(0)`. The moment the CLI prints anything (usage, read error) the process exits. With `--file=` given, that branch never fires, `consoleOutput` never changes, and the target runs on as before — both cases verified on transpiler. This is also what ends a no-args run that would otherwise park forever waiting for an LLM reply that can never arrive (there is still no timeout).

## Kotlin/Compose gotchas (example/ver-android)

- **No `package` line means the ROOT package**, which is unreachable from any packaged file. An undeclared `RootVM` sitting in `org/opengamestudio/root/` still gave `Unresolved reference 'RootVM'` from `MainActivity.kt`. Declare `package org.opengamestudio` explicitly (flat, NOT dir-matching) so `RootVM`, `RootView` and the generated `rootSet`/`F` all resolve with zero imports.
- **`by mutableStateOf("")` vs `var x = mutableStateOf("")`**: with the `by` delegate the property IS a `String` (needs `getValue`+`setValue` in scope); without it the property is a `MutableState<String>` and every access needs `.value`. Only `.value` registers a Compose snapshot read/write, so the bare form never recomposes — both are reactive, they just differ at the call site. `import androidx.compose.runtime.*` covers all three.
- **Collapsed imports**: wildcard the package families only — `androidx.compose.foundation.layout.*`, `androidx.compose.ui.*`, `androidx.compose.ui.unit.*` — and keep leaf symbols explicit (`Button`, `Text`, `Composable`, `FontFamily`), matching `MainActivity.kt`.
- **`./gradlew` needs an explicit JDK**: without `JAVA_HOME` pointing at Android Studio's JBR it dies with "Unable to locate a Java Runtime" even though `gradle/jdks/` has a cached toolchain.
- **A Kotlin `object` cannot be constructed — no `Foo()` call.** `RootComponent` is declared `object RootComponent`, so `val root = RootComponent()` is a hard compile error; report it as `Unresolved reference 'RootComponent'` at the call site and then, misleadingly, `Unresolved reference 'ctrl'` / `Unresolved reference 'setup'` on the *next* lines (the compiler infers an error type for `root`, so every member access on it fails too — fix the constructor call and those two cascade errors vanish on their own). The correct form is `val root = RootComponent` — an `object` declaration's NAME is the singleton, so it type-infers without parentheses and the existing `root.ctrl` / `root.setup()` call sites stay valid. Swift's `RootComponent.shared` idiom has no Kotlin spelling at all, because the `object` declaration *is* the singleton.
- **GRADLE CACHES A BROKEN BUILD — use `--rerun-tasks` when verifying a source change.** A file with Swift syntax inside a `.kt` file (i.e. a source file that cannot possibly compile) still reported `BUILD SUCCESSFUL`, because the Kotlin compile task was UP-TO-DATE from a previous run and never re-read the file. `touch`ing the file is not enough either. Always run `JAVA_HOME=… ./gradlew :app:compileDebugKotlin --offline --rerun-tasks` (and grep for `^e:`, since `BUILD SUCCESSFUL` is worthless as a signal here) when a change is supposed to have moved the compile from failing to passing.
- **`AGENTS.md` goes stale silently — re-read it before trusting it.** The cached-build trap above hid a `.kt` file that had held raw Swift for a long time, while the doc confidently described the Kotlin port as "inert until a later step". When a bullet contradicts what the source actually says, the SOURCE is right: `git log -p -- components/kotlin/kotlinConst.swift` showed `KOTLIN_SET_T`'s body had been uncommented in commit `fa00457` ("gen set") long before, and `MainActivity.kt` had been rewired to call `root.setup()` unconditionally. Treat any "X is not wired up yet" / "X is commented out" claim as a to-verify assertion, and grep the actual file + its git history before planning work on the assumption it is still true.
- **`other.kt` is the Kotlin twin of `other.swift`** (the console-logging helpers `otherPrintStderr` + `otherSetupConsoleLogging`). Swift→Kotlin mappings that matter: parameter labels vanish (`_ txt: String` → `txt: String`), `FileHandle.standardError.write` → `System.err.println`, `\(` interpolation → `$`, and `{ c -> Void in` → `{ c ->` (the `in` would not compile here — see the lambda traps above). The `package org.opengamestudio` line is mandatory even though the file lives in the `other/` subdir, for the same zero-import reason as `root/android/`.

## Code layout

- **Alphabetical ordering is enforced** — this is not a suggestion, new code that violates it is a bug. ASCII collation is the tiebreaker, so case matters: `entityFieldTypes` precedes `entityFields` because `T` (0x54) < `s` (0x73). The following are all sorted:
  - `F` constants, context struct fields, `field<T>`/`setField` branches, generated should-functions, and the items inside the RegisterShoulds/RegisterEffects lists
  - functions *within* a component file (`kotlinFun.swift` runs `kotlinContextName` -> `kotlinFields` -> `kotlinSet` -> `kotlinSets`; `ymlFun.swift`/`ymlConst.swift`/`swiftFun.swift`/`swiftConst.swift` likewise)
  - constants, which group by suffix-family first (`FIELD*`, `SET*`, `SUFFIX_*`, `TYPE*`) and are alphabetical inside the family with the UNDERSCORE IGNORED — hence `KOTLIN_FIELD_T` before `KOTLIN_FIELDS_T` and `SWIFT_SET_SUFFIX` before `SWIFT_SET_T`
  - the named arguments of EVERY call that takes named arguments, composable or not, across the Kotlin sources — `Box(contentAlignment = …, modifier = …)`, `Column(horizontalAlignment = …, modifier = …, verticalArrangement = …)`, `Text(fontSize = …, text = …)`, `enableEdgeToEdge(navigationBarStyle = …, statusBarStyle = …)`. Reordering named arguments is behaviour-preserving, so this is pure consistency; sorting `MainActivity.kt` the same way as `RootView.kt` is expected, not optional.
  - a trailing comma rides along with its argument, so sorting may move or remove it (`Box` loses the comma on its last arg, `enableEdgeToEdge` keeps its own)
- **The one thing that is NOT sorted**: chains of modifiers/calls read as a pipeline, so they stay in application order (`Modifier.fillMaxSize().background(ComposeColor.White)`, `super.onCreate(savedInstanceState)`) — sorting the receivers would read as a bug.

## KD (Kotlin Dialect) reference — see ref/kotlin-dialect

We're porting this to Swift as dialect v4

- **Redux-like architecture**: Controller/Context (Store), Shoulds (Reducers), Effects
- **KDContext** protocol: `recentField: String`, `field<T>(name)`, `fieldAny(name)`, `selfCopy()`, `setField(name, value)` — selfCopy lets the controller treat derived contexts uniformly
- **KDController**: accumulates a `queue` of context snapshots, each with `recentField` set. `set()` copies context, applies mutation, queues it, runs `processQueue()`. `executeFunctions()` applies queued mutation then runs every should-function; a function re-queues only if it changed a field (`recentField != KD_FIELD_NONE ("none")`). Recursion blocked via `isProcessingQueue`.
- **Should-functions (reducers)**: receive a context copy, return a new context. SSOT rule: **only one should-function may write a given field** (name them `shouldReset<FieldName>` style; combine branches that write the same field into one function, e.g. `cliShouldResetConsoleOutput` holds both "no file arg" and "input error" branches).
- **CLIError**: enum in `components/cli/cliAux.swift` (conforming to Error) for should/effect error signaling; effect funcs `throw` rather than doing multiple `cliSet` writes, so each field has exactly one write site.
- **Entity types** in kd.yml: `context`, `struct`, `should`; fields typed; `output:` section declares codegen targets (`type: kotlin|swift|c++hdr|c++sdk|c++src|jsexport`); `prefix-kotlin`/`raw*` for code insertion; `F` struct holds field-name string constants used in conditions like `c.recentField == F.didSetup`.
- **Klin**: Original KD codegen is a Node.js app built from Kotlin. Dialect v4 is reimplementing this in Swift.
