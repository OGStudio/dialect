# Dialect

Declarative reactive state management for macOS. This is a **new Swift port ("v4")** of the Kotlin Dialect (KD) controller & Klin code generator. Business logic is defined in YAML ("dialect") and executed by a Swift runtime.

**SYMLINK PARITY RULE**: Whenever a new `components/<group>/<file>.swift` is added, create a matching symlink `ver-mac/src/<group>/<file>.swift -> ../../../components/<group>/<file>.swift`, or the build won't see it. Component groups live under their own dirs under `src/`: `cli/`, `yml/`, `kotlin/`, `other/` (e.g. `ver-mac/src/yml/ymlConst.swift -> ../../../components/yml/ymlConst.swift`). New yml/kotlin files (`ymlConst.swift`, `ymlFun.swift`, `kotlinConst.swift`, `kotlinFun.swift`) must be symlinked just like the cli ones. The example app has its own parity rule: a new `example/components/root/<file>` gets a symlink into `ver-mac/src/root/`, `ver-ios/src/root/` and — for the Kotlin port — `ver-android/app/src/main/kotlin/org/opengamestudio/root/<file>.kt` (the path depth there is deep: 8 `../`). Gradle/AGP does follow symlinked sources, but the symlink must exist or the file is simply not compiled.

## Build & Test

```bash
# Core Swift tests (raw swiftc, no SPM)
util/run-swift-test

# Core C tests (raw cc)
util/run-c-test

# Core Kotlin tests (kotlinc via Android Studio JBR; no kotlinc-native available)
util/run-kotlin-test

# Build generator (step-based; util/paths + util/step/* sourced by both scripts)
util/build-generator

# Generator tool (embeds core, builds, parses a YAML file & prints it)
util/run-generator <file.yaml>

# Example app (macOS)
example/util/run-mac

# Example app (iOS): regenerate the Xcode project, then build in Xcode/xcodebuild
example/util/prepare-ios

# Example app (Android): regenerate both targets, then gradlew (JDK comes from Android Studio's JBR)
example/util/prepare-android
cd example/ver-android
JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home" ./gradlew :app:assembleDebug --offline
```

**Steps**: `util/run-generator` and `util/build-generator` source `util/paths` (CORE_SWIFT, GENERATOR_COMPONENTS) and run `util/step/*` scripts in order: `embedCoreSwift` + `embedCoreKotlin` (Step 1: regenerate `components/swift/swiftConstEmb64.swift` = `let SWIFT_EMB64_CORE = base64` of core/swift + DialectController + registerOneliners, and `components/kotlin/kotlinConstEmb64.swift` = `let KOTLIN_EMB64_CORE = base64` of the Kotlin core), `buildGenerator` (Step 2: `swift build -c release`), `runGenerator` (Step 3, run-generator only). `build-generator` also sets `STEP=0` first.

## Key Concepts

- **DialectContext**: Protocol for typed field access by string name
- **DialectController**: Reactive engine — queue field mutations, process cascade
- **dialect.yml**: Declarative rules with `should` blocks, `if`/`then` conditions, plus `oneliners` mapping field-changes to effect/UI callbacks (e.g. `readFile: cliReadInputFile(c.inputFileName)`)
- **Oneliner effects**: registered via generic `registerOneliners<T>(ctrl, items:[Any]) -> T?` (from ref/kom) where items are `[fieldName, (T)->Void, ...]`; caller pins T via `let _: CLIContext? = registerOneliners(...)`. Effect funcs call `cliSet(field, value)` to push results back into the context, expanding the cascade. **IMPORTANT (Void-closure constraint)**: each callback is cast `as! (T) -> Void`, so a reaction that is a single optional-chaining *expression* (e.g. `RootVM.shared?.countText = c.countText`) infers closure type `(T) -> Void?` and crashes the cast at runtime. Reactions touching a weak/optional singleton MUST therefore force-unwrap instead (e.g. `RootVM.shared!.countText = c.countText` — safe here because `RootVM()` is created before `root.setup()`). A statement body (`if let vm = RootVM.shared { vm.countText = c.countText }`) also works (returns `Void`).
- **Multiple components**: each component (CLIComponent, YMLComponent, SwiftComponent) owns its own context + controller and registers its own oneliners/shoulds. **Cross-component bridging** is done via oneliners in the source component, e.g. CLI's `inputContents` oneliner calls `ymlSet(F.inputContents, c.inputContents)` and YML's `entities` oneliner calls `swiftSet(F.entities, c.entities)` to push values into the YML/Swift controllers (`F` field-name constants are shared/global). Each component's init must call `xxxRegisterEffects(ctrl)` (oneliners) and `xxxRegisterShoulds(ctrl)`. Swift's `out` oneliner calls `otherWriteFile(c.path, c.out)` (needs `path` field in SwiftContext).
- **`outStructs` (v4-specific, separate from `out`)**: `SwiftContext.outStructs` holds the generated *plain struct-declaration text*, produced by the `outStructs` should: when `c.recentField == F.entityFieldTypes`, `c.outStructs = swiftStructs(c.entities, c.entityTypes, c.entityFields, c.entityFieldTypes)` and `recentField` becomes `F.outStructs`. Concatenated into `out` after `outFields`. The `swiftStructs` fun (in `components/swift/swiftFun.swift`, 4 params: `entities [String]`, `entityTypes [Int:String]`, `entityFields [Int:[String]]`, `entityFieldTypes [Int:[Int:String]]`) filters entities by `entityTypes[id] == SWIFT_TYPE_STRUCT` ("struct"), then for each struct entity calls `swiftStruct(name, fields, fieldTypes)` which emits a plain `struct <Name> { var <field> = <Type>() ... }` — NO DialectContext conformance, NO recentField. The `entityTypes` dict drives which entities become plain structs vs components vs contexts. Templates: `SWIFT_STRUCT_T` (uses `%FIELDS%` placeholder, not `%ITEMS%`), `SWIFT_STRUCT_FIELD_T` (uses `%NAME%` + `%DEFAULT%`), `SWIFT_TYPE_STRUCT` ("struct").
- **`outShoulds` (v4-specific, parallel to `outStructs`/`outContexts`)**: `SwiftContext.outShoulds` holds the generated *should-function text*, produced by the `outShoulds` should: when `c.recentField == F.entityShouldBranches`, `c.outShoulds = swiftShoulds(c.entities, c.entityShoulds, c.entityShouldBranches)` and `recentField` becomes `F.outShoulds`. Concatenated into `out` after `outContexts`, so should funcs ARE generated into `dialect.swift` (no hand-written mirror needed in tmp since the `out` should). The `swiftShoulds` fun (in `components/swift/swiftFun.swift`, 3 params: `entities`, `entityShoulds [Int:[String]]`, `entityShouldBranches [Int:[Int:[ShouldBranch]]]`) collects entity ids with non-empty `entityShoulds` via `entityShoulds.keys.sorted()`, then for each should calls `swiftShould(name, contextName, branches)`. Func name = `prefix + SWIFT_SHOULD_RESET + otherCapitalize(should)` where `prefix` = contextName minus `SWIFT_SUFFIX_CONTEXT` lowercased (e.g. `cliShouldResetConsoleOutput`). Each branch emits a condition/reaction block; conditions/reactions are multi-line arrays joined via `swiftFormatShould` (8-space base indent preserving continuation). Templates: `SWIFT_SHOULD_T` (`%FUNC%`/`%CONTEXT%`/`%BRANCHES%`), `SWIFT_SHOULD_BRANCH_T` (`%ABOUT%`/`%CONDITION%`/`%REACTION%`/`%FIELD%`), `SWIFT_SHOULD_INDENTATION` ("        "), `SWIFT_SHOULD_RESET` ("ShouldReset").
- **`outContexts` (v4-specific, parallel to `outStructs`)**: `SwiftContext.outContexts` holds the generated *DialectContext struct-declaration text*, produced by the `outContexts` should: when `c.recentField == F.entityFieldTypes`, `c.outContexts = swiftContexts(c.entities, c.entityTypes, c.entityFields, c.entityFieldTypes)` and `recentField` becomes `F.outContexts`. Concatenated into `out` after `outStructs`. The `swiftContexts` fun filters entities by `entityTypes[id] == SWIFT_TYPE_CONTEXT` ("context"), then for each context entity calls `swiftContext(name, fields, fieldTypes)` which emits a full `struct <Name>: DialectContext { var <field> = <Type>() ... var recentField = "" func field<T>... mutating func setField... }`. Templates: `SWIFT_CONTEXT_T` (uses `%ITEMS%` + `%GETTERS%` + `%SETTERS%`), `SWIFT_CONTEXT_FIELD_T` (uses `%NAME%` + `%DEFAULT%`), `SWIFT_CONTEXT_GETTER_T` (uses `%NAME%`), `SWIFT_CONTEXT_SETTER_T` (uses `%NAME%` + `%TYPE%`), `SWIFT_TYPE_CONTEXT` ("context").
- **`outSets` (v4-specific, parallel to `outShoulds`)**: `SwiftContext.outSets` holds the generated *`<component-prefix>Set()` function text* (e.g. `cliSet`/`swiftSet`/`ymlSet`/`rootSet`), produced by the `outSets` should: when `c.recentField == F.entities`, `c.outSets = swiftSets(c.entities)` and `recentField` becomes `F.outSets`. Concatenated into `out` after `outContexts` and before `outShoulds`, so Set funcs ARE generated into `dialect.swift` (no hand-written mirror in tmp). `swiftSets` (in `components/swift/swiftFun.swift`, 1 param: `entities [String]`) filters entities by `hasSuffix(SWIFT_SUFFIX_COMPONENT)` ("Component") and calls `swiftSet(entity)` per component. Func name = `prefix + SWIFT_SET_SUFFIX` ("Set") where `prefix` = contextName minus `'Context'` lowercased (e.g. `CLIComponent` → `cliSet`). Template: `SWIFT_SET_T` (`%FUNC%`/`%COMPONENT%`). Registers nothing; effects/components call these generated funcs directly.
- **Kotlin `outSets` (parallel to the Swift one)**: `KotlinContext.outSets` holds the generated *Kotlin* `<component-prefix>Set()` function text, produced by the `outSets` should: when `c.recentField == F.entities`, `c.outSets = kotlinSets(c.entities)` and `recentField` becomes `F.outSets`. Concatenated into `out` after `outContexts` and before `outShoulds`. `kotlinSets` (in `components/kotlin/kotlinFun.swift`, 1 param: `entities [String]`) mirrors `swiftSets`: filters entities by `hasSuffix(KOTLIN_SUFFIX_COMPONENT)` ("Component") and calls `kotlinSet(entity)` per component; `kotlinSet` derives the func name as `prefix + KOTLIN_SET_SUFFIX` ("Set") from `kotlinContextName(entity)` (Component→Context) minus `'Context'`, lowercased. Templates: `KOTLIN_SET_T` (`%FUNC%`/`%COMPONENT%`). The emitted Kotlin body is commented out — `//%COMPONENT%.singleton!!.ctrl.set(key, value)` — because generated Kotlin component classes (with `singleton`) do not exist yet, so an uncommented body would not compile. Consequence: the Set funcs resolve and are callable (e.g. `rootSet(F.didClickIncrement, true)` from a hand-written view) but are inert until a later step generates Kotlin components and the `//` is dropped. `KotlinComponent` currently has no `type: kotlin` entry in the generator's `dialect.yml` `output:` section, so `c.path` stays empty and `otherWriteFile` is a no-op — the Kotlin `out` is currently only visible via console logging.
- **Kotlin `outFields` (parallel to the Swift one)**: `KotlinContext.outFields` holds the generated *Kotlin* `object F` field-name-constant text, produced by the `outFields` should: when `c.recentField == F.entityFields`, `c.outFields = kotlinFields(c.entityFields)` and `recentField` becomes `F.outFields`. Concatenated into `out` BEFORE `outSets`, so the emitted `F` is available to the Set funcs and to hand-written Kotlin component code (e.g. `rootSet(F.didClickIncrement, true)`). `kotlinFields` (in `components/kotlin/kotlinFun.swift`, 1 param: `entityFields [Int:[String]]`) mirrors `swiftFields` exactly — collects field names into a `Set<String>`, emits `KOTLIN_FIELD_T` per name in `names.sorted()`, wraps them via `KOTLIN_FIELDS_T`. `struct F`/`static let` become `object F`/`const val`. Templates: `KOTLIN_FIELDS_T` (`%ITEMS%`), `KOTLIN_FIELD_T` (`%NAME%`). The `out*` sections are all populated now: `outFields`, `outStructs`, `outContexts`, `outSets`, `outShoulds`, `outRegisterShoulds`, `outRegisterEffects`.
- **Kotlin `outStructs` (parallel to the Swift one)**: `KotlinContext.outStructs` holds the generated *Kotlin* `data class` declarations, produced by the `outStructs` should: when `c.recentField == F.entityFieldTypes`, `c.outStructs = kotlinStructs(c.entities, c.entityTypes, c.entityFields, c.entityFieldTypes)` and `recentField` becomes `F.outStructs`. Concatenated into `out` BETWEEN `outFields` and `outSets`, mirroring the Swift order (`outFields + outStructs + outContexts + outSets`).
- **Kotlin type mapping (no Swift equivalent)**: the dialect's type spelling is valid Swift but NOT valid Kotlin, so `outStructs` needs two mappers that `swiftStruct` never had: `kotlinType` (`Bool` → `Boolean`; `[X]` → `Array<kotlinType(X)>`; `[K: V]` → `Map<kotlinType(K), kotlinType(V)>`; anything else passes through — `String`/`Int`/`OutputPath` are already valid Kotlin) and `kotlinTypeDefaultValue` (`""`/`0`/`false`, `arrayOf()` for a bracketed type without a `:`, `mapOf()` for one with a `:`, `%TYPE%()` for a bare named type). `Bool` is the only primitive that actually changes, which is why `KOTLIN_TYPE_BOOL = "Bool"` exists next to `KOTLIN_MAPPED_BOOL = "Boolean"` (the `KOTLIN_TYPE_*` family holds dialect spellings, `KOTLIN_MAPPED_*` holds Kotlin spellings). `KOTLIN_MAP_T` uses two placeholders (`%KEY%`/`%VALUE%`), NOT `%TYPE%` twice — `replacingOccurrences` replaces ALL occurrences, so a repeated placeholder would map key and value to the same type.
- **`kotlinTypeParts` must count bracket depth**: the dialect nests (`[Int: [Int: [ShouldBranch]]]` → `Map<Int, Map<Int, Array<ShouldBranch>>>`), so splitting on `":"` naively yields 3 parts instead of 2. It walks the string tracking `[`/`]` depth and only splits at depth 0, trimming the space after each colon via `drop(while: { $0 == " " })`. Templates: `KOTLIN_STRUCT_T` (`%NAME%`/`%FIELDS%`), `KOTLIN_STRUCT_FIELD_T` (`%NAME%`/`%TYPE%`/`%DEFAULT%`, trailing comma so the list is valid Kotlin), plus `KOTLIN_LIST_T` (`%TYPE%`) and `KOTLIN_MAP_T`. The `%FIELDS%`-on-its-own-line shape (inherited from `SWIFT_STRUCT_T`) leaves a cosmetic blank line before the closing `)`: `SWIFT_STRUCT_T` does the same in Swift, so the two ports match.
- **Kotlin `outContexts` (parallel to the Swift one)**: `KotlinContext.outContexts` holds the generated *Kotlin* `data class` context declarations, produced by the `outContexts` should: when `c.recentField == F.entityFieldTypes`, `c.outContexts = kotlinContexts(c.entities, c.entityTypes, c.entityFields, c.entityFieldTypes)`. Concatenated into `out` AFTER `outStructs`, mirroring Swift's `outFields + outStructs + outContexts + outSets`. `kotlinContexts`/`kotlinContext` mirror `swiftContexts`/`swiftContext` (same 4 params, filters by `KOTLIN_TYPE_CONTEXT`, same `%ELSE%` first-branch-omits-`else` trick), but there are three Kotlin-specific differences Swift never had:
  - **`override var recentField: String = ""` is a CONSTRUCTOR PARAM, not a body property.** Swift structs are value types so a whole-struct copy carries `recentField` for free; a Kotlin `data class` `copy()` only copies constructor params, and `DialectController` relies on `f(context.selfCopy())` seeing the *current* `recentField` (every should's first branch is `if c.recentField == F.x`). As a body property it would go stale and every should would miss its trigger. Being a param also gives the no-arg constructor for free (Kotlin synthesises one when all params have defaults), which is what `DialectController(KotlinContext())` needs — and it keeps a field-less context valid.
  - **`selfCopy()` is NOT defaulted in the Kotlin core.** `core/kotlin/DialectContext.kt` implements only `fieldAny` with a body; `selfCopy()` is an abstract member, so the generated class must provide `override fun selfCopy(): DialectContext = this.copy()`.
  - **`@Suppress("UNCHECKED_CAST")` goes on the CLASS, once — not on `field` and `setField` separately.** `as T` is unchecked, and so is `value as Map<Int, String>` / `value as Array<String>` in `setField` — erasing to a *generic* type is unchecked, so a `Boolean`/`String`/`Int` setter is warning-free but every `Array`/`Map` field warns. One annotation above `data class %NAME%(` covers every member; annotating only `field` still left ~10 warnings for `KotlinContext`, and annotating each function is noise. Templates: `KOTLIN_CONTEXT_T` (`%NAME%`/`%FIELDS%`/`%GETTERS%`/`%SETTERS%`), `KOTLIN_CONTEXT_FIELD_T` (`%NAME%`/`%TYPE%`/`%DEFAULT%`), `KOTLIN_CONTEXT_GETTER_T` (`%ELSE%`/`%NAME%`), `KOTLIN_CONTEXT_SETTER_T` (`%ELSE%`/`%NAME%`/`%TYPE%` — the `%TYPE%` is the MAPPED Kotlin type here, unlike `swiftContext` which passes the dialect type through verbatim). The `%FIELDS%` line also leaves the same cosmetic blank line before `override var recentField` that Swift has before its `var recentField`.
- **Kotlin `outShoulds` (parallel to the Swift one)**: `KotlinContext.outShoulds` holds the generated should-function text, produced by the `outShoulds` should: when `c.recentField == F.entityShouldBranches`, `c.outShoulds = kotlinShoulds(c.entities, c.entityShoulds, c.entityShouldBranches)`. Concatenated into `out` after `outSets`, mirroring the Swift order. `kotlinShoulds`/`kotlinShould` (in `components/kotlin/kotlinFun.swift`, 3 params: `entities`, `entityShoulds [Int:[String]]`, `entityShouldBranches [Int:[Int:[ShouldBranch]]]`) mirror `swiftShoulds`/`swiftShould` exactly — same `keys.sorted()` collection, same func name `prefix + KOTLIN_SHOULD_RESET + otherCapitalize(should)`, same `swiftFormatShould`-equivalent `kotlinFormatShould` (8-space base indent).
  - **THE SHOULD SOURCE IS SWIFT, SO THE KOTLIN BRANCHES ARE NO-OPS BY DESIGN.** The `condition`/`reaction` arrays in dialect.yml are verbatim Swift expressions (`c.countText = "Count: '\(c.count)'"`, `cliArgumentValue(c.arguments, CLI_ARG_FILE).isEmpty`) that cannot compile in Kotlin. Each branch is therefore emitted as `if (false) { /** condition */ /** reaction */ c.recentField = F.<field>; return c }` — the Swift text is preserved verbatim in `/** ... */` block comments (NOT `//`, because the multi-line Swift bodies would need one `//` per line), and the `if (false)` makes the branch unreachable so the compiler accepts it. Consequence: every should falls through to `c.recentField = DIALECT_CONTEXT_RECENT_FIELD_NONE`, which is the engine's "this should changed nothing, do not re-queue" signal (`DialectController.executeFunctions` only re-queues a should whose `recentField != DIALECT_CONTEXT_RECENT_FIELD_NONE`). So the Kotlin engine runs but the shoulds are inert until they are hand-ported.
  - **Two `/** */` blocks per branch, not one**: the condition and the reaction are separately wrapped, mirroring the Swift template's two `%CONDITION%`/`%REACTION%` placeholders and keeping the two source fragments independently copy-pasteable when porting.
  - **The Swift comments sit INSIDE the `if (false)`, not before it** — so un-commenting a block in place is all that is needed to start a port, and the `if (false)` can be flipped to `if (true)` once the fragments compile.
  - **`val c = c` NOT `var c = c`**: Swift needs `var c = c` to mutate its struct copy; a Kotlin `data class` copy is itself mutable (`recentField` is a `var` constructor param), so `val` is correct and mirrors intent better. The generated signature is `fun %FUNC%(c: %CONTEXT%): %CONTEXT%` — Kotlin has no argument labels by default, hence no leading `_` where Swift writes `_ c: CLIContext`.
  - The `%ABOUT%` marker uses `//` (a `//` comment survives fine as a single line) where the Swift template uses `/* */`. Templates: `KOTLIN_SHOULD_T` (`%FUNC%`/`%CONTEXT%`/`%BRANCHES%`), `KOTLIN_SHOULD_BRANCH_T` (`%ABOUT%`/`%CONDITION%`/`%REACTION%`/`%FIELD%`), `KOTLIN_SHOULD_INDENTATION` ("        "), `KOTLIN_SHOULD_RESET` ("ShouldReset").
  - **A `/** */` comment cannot nest `*/`**: the dialect's Swift bodies contain no nested block comments today, but a yml should whose reaction embeds a literal `*/` (e.g. inside a string) would terminate the comment early and break the Kotlin output.
- **Adding an `out*` section needs THREE things, not one**: the codegen fun + templates, the should in `dialect.yml`, AND the YML→Kotlin bridge for whatever field the should keys on. `outStructs` keys on `entityFieldTypes`, so without `entityFieldTypes: kotlinSet(...)` **and** `entityTypes: kotlinSet(...)` the should can never fire — the `KotlinContext` fields simply stay empty and `outStructs` silently stays `""` with no error anywhere. Check the regenerated `dialect.swift` contains the new `kotlinSet(F.<field>, c.<field>)` lines inside `ymlRegisterEffects`. Two Kotlin lambda traps bite at the compile-verify step (both reproduced standalone against `kotlinc` 2.3.10, K2 frontend): a single-parenthesised lambda param `{ (c: T) -> }` is a **destructuring declaration**, not a one-param lambda, so it fails with `cannot infer type for implicit value parameter 'it'` plus a flood of `component1() is ambiguous` candidates — and the `{ x in ... }` implicit-param shorthand is rejected outright with `unresolved reference 'x'`. Always write `{ c: T -> ... }` / `{ f -> ... }` with explicit `->`.
- **Kotlin `out` (final concatenation)**: `KotlinContext.out` = `KOTLIN_OGS_PKG + "\n" + otherBase64ToString(KOTLIN_EMB64_CORE).replacingOccurrences(of: KOTLIN_OGS_PKG, with: "") + c.outFields + c.outStructs + c.outContexts + c.outSets + c.outShoulds + c.outRegisterShoulds + c.outRegisterEffects` — package line, then the embedded Kotlin core (package line stripped), then `object F`, then the structs, then the contexts, then the Set funcs, then the should funcs, then the RegisterShoulds funcs, then the RegisterEffects funcs last. The order mirrors the Swift `out` exactly. The `out` should also declares `path` resolved from `outputPaths` matching `KOTLIN_TYPE`.
- **Kotlin `outRegisterShoulds` (parallel to the Swift one)**: `KotlinContext.outRegisterShoulds` holds the generated `<component-prefix>RegisterShoulds()` function text, produced by the `outRegisterShoulds` should: when `c.recentField == F.entityShoulds`, `c.outRegisterShoulds = kotlinRegisterShoulds(c.entities, c.entityShoulds)` and `recentField` becomes `F.outRegisterShoulds`. Appended after `outShoulds`. `kotlinRegisterShoulds`/`kotlinRegisterShould` (2 params: `entities [String]`, `entityShoulds [Int:[String]]`) mirror the Swift pair exactly — same `entityShoulds.keys.sorted()` collection, same func name `prefix + KOTLIN_REGISTER_SHOULDS_SUFFIX`, same should-func name `prefix + KOTLIN_SHOULD_RESET + otherCapitalize(should)`. Templates: `KOTLIN_REGISTER_SHOULDS_T` (`%FUNC%`/`%CONTEXT%`/`%ITEMS%`), `KOTLIN_REGISTER_SHOULDS_ITEM_T` (`%SHOULD%`), `KOTLIN_REGISTER_SHOULDS_SUFFIX` ("RegisterShoulds"). Three deliberate Kotlin deviations from the Swift body: (1) the items are `::shouldFunc` **function references**, not bare function names — Kotlin has no implicit reference syntax, so the bare-name Swift list becomes a `listOf(...)` of `::name`s; (2) the cast is `f(c as <Context>)`, a plain downcast, so it needs no `as!`; (3) lambda params use `{ f -> ... }` / `{ c -> ... }` with an explicit `->` because **this project's `kotlinc` (2.3.10, K2 frontend) rejects the `{ x in ... }` implicit-parameter shorthand outright** — it reports `unresolved reference 'x'`. Registration compiles and runs, but the shoulds it registers are the no-op ones described in Kotlin `outShoulds`, so `recentField` stays `DIALECT_CONTEXT_RECENT_FIELD_NONE` and no re-queue happens.
- **Kotlin `outRegisterEffects` (parallel to the Swift one)**: `KotlinContext.outRegisterEffects` holds the generated `<component-prefix>RegisterEffects()` function text, produced by the `outRegisterEffects` should: when `c.recentField == F.entityOneliners`, `c.outRegisterEffects = kotlinRegisterEffects(c.entities, c.entityOneliners)` and `recentField` becomes `F.outRegisterEffects`. Appended last in `KotlinContext.out`. `kotlinRegisterEffects`/`kotlinRegisterEffect` (2 params: `entities [String]`, `entityOneliners [Int:[Oneliner]]`) mirror the Swift pair exactly — same `entityOneliners.keys.sorted()` collection, same non-empty filter, same func name `prefix + KOTLIN_REGISTER_EFFECTS_SUFFIX`. Templates: `KOTLIN_REGISTER_EFFECTS_T` (`%FUNC%`/`%ITEMS%`), `KOTLIN_REGISTER_EFFECT_ITEM_T` (`%FIELD%`/`%REACTION%`), `KOTLIN_REGISTER_EFFECTS_SUFFIX` ("RegisterEffects"). Three Kotlin-specific differences: (1) **no `let _: <Context>? =` type pin** — Swift needs it to infer the generic `T` in `registerOneliners<T>`; the Kotlin core's `registerOneliners(ctrl: DialectController, items: Array<Any>)` is not generic, so the `let _ =` trick does not exist and simply calling it is correct; (2) the item is `{ c: DialectContext -> ... }` — **unparenthesized and typed as the PROTOCOL**, because `registerOneliners` casts the callback back to `(c: DialectContext) -> Unit`, so a `{ (c: KotlinContext) -> }` lambda would not match the cast and would throw `ClassCastException` on the first mutation. A parenthesized single param `{ (c: DialectContext) -> }` is parsed as a **destructuring declaration**, which fails with `cannot infer type for implicit value parameter 'it'` — hence both parens and the wrong type must be avoided together; (3) as with `outShoulds`, each reaction is a Swift expression (`print(c.countText)`, `RootVM.shared!.countText = c.countText`, `otherWriteFile(c.path, c.out)`) so it is emitted as `if (false) { /** <swift> */ }` via `kotlinFormatShould([oneliner.reaction])`, using the same 8-space indent as the should branches. The callbacks ARE registered, so the engine's field-callback dispatch reaches them and they no-op safely. Note `entityOneliners` needed a Kotlin bridge to be reachable at all — see the YML→Kotlin bridges bullet.
- **YML→Kotlin bridges**: `YMLComponent` feeds Kotlin with oneliners `entities: kotlinSet(F.entities, c.entities)` (drives `outSets`), `entityFields: kotlinSet(F.entityFields, c.entityFields)` (drives `outFields`), `entityFieldTypes: kotlinSet(F.entityFieldTypes, c.entityFieldTypes)` + `entityTypes: kotlinSet(F.entityTypes, c.entityTypes)` (both drive `outStructs`), `entityShoulds: kotlinSet(F.entityShoulds, c.entityShoulds)` (drives `outRegisterShoulds`), `entityShouldBranches: kotlinSet(F.entityShouldBranches, c.entityShouldBranches)` (drives `outShoulds`), `entityOneliners: kotlinSet(F.entityOneliners, c.entityOneliners)` (drives `outRegisterEffects`) and `outputPaths: kotlinSet(F.outputPaths, c.outputPaths)` (drives `KotlinContext.path`). Bridges are `entities`, `entityFields`, `entityFieldTypes`, `entityTypes`, `entityShoulds`, `entityShouldBranches`, `entityOneliners`, `outputPaths` — i.e. **every** field the Kotlin `out*` sections key on, so nothing is Swift-only anymore. In the oneliners list each `kotlinSet(...)` line sits immediately BEFORE its `swiftSet(...)` twin so the two ports stay paired.
- **Android port (example/ver-android)**: a syntactic Compose mirror of the Swift example, not a port of the *engine* — the engine still comes from the generated `dialect.kt` (embedded `KOTLIN_EMB64_CORE` + `object F` + `rootSet`). `rootVM.kt` is `object RootVM { var countText by mutableStateOf("") }`: Swift's `ObservableObject` + `@Published` becomes `mutableStateOf` behind a `by` delegate, and Swift's `static private(set) weak var shared` is **dropped entirely** because a Kotlin `object` IS the singleton (so `RootView()` takes no VM param, unlike Swift's `RootView(_ vm: RootVM)`). Both component files declare the FLAT `package org.opengamestudio` (same as the generated `dialect.kt`) rather than dir-matching `org.opengamestudio.root[.view]` — that keeps `RootVM` and `rootSet` resolvable with **zero imports**, mirroring Swift's single-module access. The generated `RootContext` (`count: Int`, `countText: String`, `didClickIncrement: Boolean`, `didLaunch: Boolean`, `didSetup: Boolean`) arrives via `outContexts` with `Bool` already mapped to `Boolean`, and `rootRegisterShoulds`/`rootRegisterEffects` arrive alongside it — but nothing references them yet: `MainActivity.kt` still has its `//RootComponent.setup()` block commented out. Making the counter actually move needs, in order: a Kotlin `RootComponent` class (`singleton` + `ctrl`), dropping the `//` in `KOTLIN_SET_T`, and rewriting the example's `countText: RootVM.shared!.countText = c.countText` oneliner for the object form (the context, should, and registration sides are now generated; only the should *bodies* and effect *reactions* remain commented-out Swift).
- **`outRegisterShoulds` (v4-specific, parallel to `outSets`/`outShoulds`)**: `SwiftContext.outRegisterShoulds` holds the generated *`<component-prefix>RegisterShoulds()` function text* (e.g. `cliRegisterShoulds`/`swiftRegisterShoulds`/`ymlRegisterShoulds`/`rootRegisterShoulds`), produced by the `outRegisterShoulds` should: when `c.recentField == F.entityShoulds`, `c.outRegisterShoulds = swiftRegisterShoulds(c.entities, c.entityShoulds)` and `recentField` becomes `F.outRegisterShoulds`. Concatenated into `out` AFTER `outShoulds`, so RegisterShoulds funcs ARE generated into `dialect.swift` and must NOT be hand-written in tmp anymore (components call the generated register funcs directly). `swiftRegisterShoulds` (in `components/swift/swiftFun.swift`, 2 params: `entities [String]`, `entityShoulds [Int:[String]]`) collects entity ids via `entityShoulds.keys.sorted()`, then for each component calls `swiftRegisterShould(contextName, shoulds)` which emits a `func <prefix>RegisterShoulds(_ ctrl: DialectController)` registering `prefix + SWIFT_SHOULD_RESET + otherCapitalize(should)` per should. Templates: `SWIFT_REGISTER_SHOULDS_T` (`%FUNC%`/`%CONTEXT%`/`%ITEMS%`), `SWIFT_REGISTER_SHOULDS_SUFFIX` ("RegisterShoulds"). NOTE: overload resolution separates the codegen `swiftRegisterShoulds(entities, entityShoulds) -> String` from the generated `func swiftRegisterShoulds(_ ctrl: DialectController)` — same pattern as `swiftSet` codegen vs generated Set funcs.
- **`outRegisterEffects` (v4-specific, parallel to `outRegisterShoulds`)**: `SwiftContext.outRegisterEffects` holds the generated *`<component-prefix>RegisterEffects()` function text* (e.g. `cliRegisterEffects`/`swiftRegisterEffects`/`ymlRegisterEffects`/`rootRegisterEffects`), produced by the `outRegisterEffects` should: when `c.recentField == F.entityOneliners`, `c.outRegisterEffects = swiftRegisterEffects(c.entities, c.entityOneliners)` and `recentField` becomes `F.outRegisterEffects`. Concatenated into `out` AFTER `outRegisterShoulds` (very last section), so RegisterEffects funcs ARE generated into `dialect.swift` too — ALL oneliner/effect/bridge registration is generated (`tmp.dialect.swift` was removed). `swiftRegisterEffects` (in `components/swift/swiftFun.swift`, 2 params: `entities [String]`, `entityOneliners [Int:[Oneliner]]`) collects entity ids with non-empty oneliners via `entityOneliners.keys.sorted()`, then for each component calls `swiftRegisterEffect(contextName, oneliners)` which emits a `func <prefix>RegisterEffects(_ ctrl: DialectController)` body `let _: <Context>? = registerOneliners(ctrl, [...] )` with one item `F.<field>, { (c: <Context>) in <reaction> },` per Oneliner (reaction used verbatim from yml). Templates: `SWIFT_REGISTER_EFFECTS_T` (`%FUNC%`/`%CONTEXT%`/`%ITEMS%`), `SWIFT_REGISTER_EFFECTS_SUFFIX` ("RegisterEffects"). NOTE: overload resolution separates the codegen `swiftRegisterEffects(entities, entityOneliners) -> String` from the generated `func swiftRegisterEffects(_ ctrl: DialectController)` — same pattern as `swiftRegisterShoulds`/`swiftSet`.
- **`out` (final concatenation)**: `SwiftContext.out` = `otherBase64ToString(SWIFT_EMB64_CORE) + c.outFields + c.outStructs + c.outContexts + c.outSets + c.outShoulds + c.outRegisterShoulds + c.outRegisterEffects`. This ordering (GENERATED core first, then F, structs, contexts, Set funcs, should funcs, RegisterShoulds funcs, then RegisterEffects funcs last) means ALL target code is fully generated — `ver-mac/src/dialect.swift` is the only generator source file. The `out` should also declares `path` (Swift output path) resolved from `outputPaths` matching `SWIFT_TYPE`.
- **CHICKEN-EGG / struct F upkeep (critical)**: `F` (`struct F { static let ... = "<name>" }`) is a field-name constant struct. It is defined ONLY in the **generated** `ver-mac/src/dialect.swift` (`struct F` is generated via `swiftFields`/`outFields`; nothing references `F.*` before `dialect.swift` compiles). `dialect.swift` cannot be regenerated in strict purity (regen needs the built generator, which needs dialect.swift). So **whenever dialect.yml adds a new field to any context, you MUST hand-patch the new `static let <field> = "<field>"` into the generated `ver-mac/src/dialect.swift` struct `F`**, placed in ASCII-alphabetical order between its siblings (e.g. `outStructs` goes between `outFields` and `outputPaths` — `S`(0x53) < `p`(0x70)). Skip this and the build fails (`F.outStructs` unresolved). This hand-patch is exactly what a future regen would emit, so it stays consistent. The generated **should funcs** (which live in `dialect.swift` via `outShoulds`) also reference `F.*` — hand-patching `F` keeps those self-consistent at build/run.
- **Chicken-egg checklist (when SSOT dialect.yml gains a field on a context — e.g. `entityFieldTypes` + `outStructs` on SwiftContext)**: (1) hand-patch the `static let <field> = "<field>"` into the generated `ver-mac/src/dialect.swift` struct `F`, alphabetically; (2) if another component's oneliner should feed it (YML→Swift bridge), add its oneliner in `dialect.yml` (e.g. `entityFieldTypes: swiftSet(F.entityFieldTypes, c.entityFieldTypes)` — this both feeds `SwiftContext.entityFieldTypes` and, via `recentField`, triggers the generated `swiftShouldResetOutStructs`); the bridge regenerates into `ymlRegisterEffects` via `outRegisterEffects` (regen-stability: build → regen → verify byte-identical, update hash). Context struct vars, `field<T>`/`setField` branches, should funcs, Set funcs, and RegisterShoulds/RegisterEffects funcs are NO LONGER hand-written — they regenerate via `swiftContexts`/`outContexts`, `swiftShoulds`/`outShoulds`, `swiftSets`/`outSets`, `swiftRegisterShoulds`/`outRegisterShoulds`, `swiftRegisterEffects`/`outRegisterEffects`.
- **Per-component helper files** (components/yml/): `ymlConst.swift` (global constants like `YML_PREFIX_VERSION`), `ymlFun.swift` (pure helpers/parsers like `ymlParseVersion`), `ymlEffect.swift` (effects that `ymlSet` results back), `ymlAux.swift` (aux/print helpers). Matching `cliConst/cliFun/cliEffect/cliAux`.
- **YML schema parsing** (chunks): input is split into **chunks** = `[String: [String]]` keyed by the chunk's first (non-indented) line. Blank lines (`""`) delimit chunks — detected by `ymlIsLineChunkStart`/`ymlIsLineChunkEnd`. Downstream parsers consume structures: `ymlParseEntities` (top-level `Key:` lines, `hasSuffix(":")`), `ymlParseEntityTypes` (indented `type:` under each entity, `YML_PREFIX_TYPE` bakes in the 4-space indent), `ymlParseVersion` (from the chunk key prefix `YML_PREFIX_VERSION`). Should-chains cascade: `inputLines` → `chunks`/`entities`, then `chunks` → `version`, `entities` → `entityTypes`.
- **ShouldBranch struct (renamed fields)**: dialect.yml's `ShouldBranch` struct entity has fields `about` (String), `condition` ([String]), `reaction` ([String]) — these were **renamed** from `desc`/`if`/`then` to avoid the Swift keywords `if`/`then` and match "condition/reaction" semantics. The YAML **input** markers for parsing still read `if:`/`then:` (prefixed lines), but they map into `condition`/`reaction` fields via `isParsingCondition`/`isParsingReaction` flags in `ymlParseEntityShouldBranches`. Generated code: `struct ShouldBranch` (plain struct, in `outStructs`) + the `F.about/condition/reaction` constants (hand-patched into the generated `dialect.swift`).
- **Rename propagation (single SSOT in dialect.yml)**: when a struct *field* is renamed in dialect.yml (like `desc/if/then` → `about/condition/reaction`), update ALL of these in one pass: (1) the `ShouldBranch` struct declaration + `F` constants in the generated `ver-mac/src/dialect.swift` (hand-patch); (2) `ymlFun.swift` — field writes (`.about`), local var names, parser flags (`isParsingCondition`/`isParsingReaction`) and their comments; (3) `swiftConst.swift` `SWIFT_SHOULD_BRANCH_T` template placeholders (`%ABOUT%`/`%CONDITION%`/`%REACTION%`); (4) `swiftFun.swift` commented `swiftShould` refs (`branch.about`, `.condition`, `.reaction`); (5) C `core/c/dialect.h` `ShouldBranch` struct (`about`/`condition`/`reaction`; the `if`→`condition` change also *removes* the old `if_` C-keyword workaround). After the rename, verify regen-stability: run `util/run-c-test`, `util/build-generator`, then `util/run-generator --file=dialect.yml` and confirm `ver-mac/src/dialect.swift` regenerates byte-identical to the hand-patch (hash matches).
- **Keyword collision conventions across ports**: Swift backticks Swift keywords (`` `if` ``, `` `type` ``); C appends `_` (former `if_`). Renaming a field away from a keyword lets you drop the escape in every port. The `if`/`then` in `ymlConst.swift` prefix constants (`YML_PREFIX_SHOULD_BRANCH_IF` = `"                if:"`, then-marker) are the *input syntax*, NOT struct fields — they intentionally keep the `if:`/`then:` spelling and are NOT part of the rename.

## Swift gotchas (learned the hard way)

- `!x.isEmpty()` parses as force-unwrap — use `!x.isEmpty` or `x != ""`.
- `String.startsWith(prefix)` is not Swift — use `hasPrefix`.
- `String.substring(from:)` is not Swift — use `dropFirst(n)`/`dropFirst(prefix.count)`.
- `String.trim()`, `find`, `indexOf`, `trimming` do NOT exist here — use `hasPrefix`/`hasSuffix`/`isEmpty`/`contains`. To strip indentation, either bake it into the `YML_PREFIX_*` constant (e.g. `"    type: "`) or loop `while s.hasPrefix(" ") { s = String(s.dropFirst(1)) }`.
- `String.split(separator:)` DEFAULTS to `omittingEmptySubsequences: true` — blank lines get silently dropped. Pass `omittingEmptySubsequences: false` when blank lines matter (chunk boundaries depend on them!).
- `Substring` is NOT implicitly convertible to `String` — `s.dropFirst(1)`/`dropLast(1)` return `Substring`; you must write `String(...)` explicitly (at assignment, `.append`, and argument boundaries).
- `[String] += someString` fails (String is treated as a character Sequence) — use `.append(someString)`.
- Kotlin-style `if cond && let x = ...` is invalid Swift — use a comma: `if cond, let x = ...`.
- `str.split("\n")` is wrong — use `str.split(separator: "\n")`. But for chunking you need the empty-subsequences variant above.
- Optionals at the boundary: `value as! Bool`/`as! String` force-casts in setField; a String field wrote from an effect must match its declared type exactly.

## Generator gotchas (learned the hard way)

- **Swift multiline-string template spacing is subtle**: the newline immediately before the closing `"""` is stripped, and only the newline right after the opening `"""` is consumed. So a template written `%ITEMS%}` ends with NO trailing newline, and the next section's single leading newline yields NO blank line between them (the generated Kotlin came out as `}\nfun cliSet(`). Mirror the `SWIFT_*_T` shapes exactly — `%ITEMS%` alone on its line, `}` on the next line, one blank line before the closing `"""` — and verify the separator with `repr()` on a slice of `/tmp/dialect.log` rather than by eye.
- **A new bridge oneliner needs TWO build+regen cycles**: the oneliner only exists in the generated `dialect.swift`, so the binary built from the *previous* `dialect.swift` does not have it yet. Correct sequence: `util/build-generator` -> `run-generator` -> `util/build-generator` -> `run-generator`, then confirm the hash is stable across one more cycle.
- **Run the generator from `generator/`**: `util/run-generator` resolves `dialect.yml` relative to the cwd, so from the repo root it fails with "Could not read file" (and still exits 0 after writing core-only artifacts).
- **`/tmp/dialect.log` is the inspection surface**: `util/step/runGenerator` hardcodes the generator's stderr there, and `otherSetupConsoleLogging` prints every field as `ИГР <Component> k/v: '<field>'/'<value>'`. That log is the ONLY way to see a log-only output such as the Kotlin `out` (the generator's own `dialect.yml` has no `type: kotlin` target, so nothing is written to disk).
- **`otherWriteFile` fails silently**: it is `try? content.write(toFile:)`, so an empty path (no matching `output:` entry) or a missing parent directory means the file is never written and the run still exits 0. Always confirm the `ИГР otherWF path/content.count:` line shows a non-empty path AND a plausible char count.
- **Compile-verify the log-only Kotlin output**: nothing writes the generator's Kotlin `out` to disk, so nothing else would catch invalid emitted Kotlin (e.g. a wrong type spelling). Extract the `ИГР Kotlin k/v: 'out'/'…'` record from `/tmp/dialect.log` — skip the value's OWN quotes as well as the field's, the payload spans many physical lines — write it to a `.kt` file and run `"/Applications/Android Studio.app/Contents/plugins/Kotlin/kotlinc/bin/kotlinc" File.kt -d out` with `JAVA_HOME` at Android Studio's JBR. To unit-test a pure codegen fun WITHOUT a regen cycle, compile its `components/*/*.swift` pair with a throwaway `main.swift` (they only reference the file's own constants).

## Kotlin/Compose gotchas (example/ver-android)

- **No `package` line means the ROOT package**, which is unreachable from any packaged file. An undeclared `RootVM` sitting in `org/opengamestudio/root/` still gave `Unresolved reference 'RootVM'` from `MainActivity.kt`. Declare `package org.opengamestudio` explicitly (flat, NOT dir-matching) so `RootVM`, `RootView` and the generated `rootSet`/`F` all resolve with zero imports.
- **`by mutableStateOf("")` vs `var x = mutableStateOf("")`**: with the `by` delegate the property IS a `String` (needs `getValue`+`setValue` in scope); without it the property is a `MutableState<String>` and every access needs `.value`. Only `.value` registers a Compose snapshot read/write, so the bare form never recomposes — both are reactive, they just differ at the call site. `import androidx.compose.runtime.*` covers all three.
- **Collapsed imports**: wildcard the package families only — `androidx.compose.foundation.layout.*`, `androidx.compose.ui.*`, `androidx.compose.ui.unit.*` — and keep leaf symbols explicit (`Button`, `Text`, `Composable`, `FontFamily`), matching `MainActivity.kt`.
- **`./gradlew` needs an explicit JDK**: without `JAVA_HOME` pointing at Android Studio's JBR it dies with "Unable to locate a Java Runtime" even though `gradle/jdks/` has a cached toolchain.

## Code layout

- **Alphabetical ordering is enforced** — this is not a suggestion, new code that violates it is a bug. ASCII collation is the tiebreaker, so case matters: `entityFieldTypes` precedes `entityFields` because `T` (0x54) < `s` (0x73). The following are all sorted:
  - `F` constants, context struct fields, `field<T>`/`setField` branches, generated should-functions, and the items inside the RegisterShoulds/RegisterEffects lists
  - functions *within* a component file (`kotlinFun.swift` runs `kotlinContextName` -> `kotlinFields` -> `kotlinSet` -> `kotlinSets`; `ymlFun.swift`/`ymlConst.swift`/`swiftFun.swift`/`swiftConst.swift` likewise)
  - constants, which group by suffix-family first (`FIELD*`, `SET*`, `SUFFIX_*`, `TYPE*`) and are alphabetical inside the family with the UNDERSCORE IGNORED — hence `KOTLIN_FIELD_T` before `KOTLIN_FIELDS_T` and `SWIFT_SET_SUFFIX` before `SWIFT_SET_T`
  - the named arguments of EVERY call that takes named arguments, composable or not, across the Kotlin sources — `Box(contentAlignment = …, modifier = …)`, `Column(horizontalAlignment = …, modifier = …, verticalArrangement = …)`, `Text(fontSize = …, text = …)`, `enableEdgeToEdge(navigationBarStyle = …, statusBarStyle = …)`. Reordering named arguments is behaviour-preserving, so this is pure consistency; sorting `MainActivity.kt` the same way as `RootView.kt` is expected, not optional.
  - a trailing comma rides along with its argument, so sorting may move or remove it (`Box` loses the comma on its last arg, `enableEdgeToEdge` keeps its own)
- **The one thing that is NOT sorted**: chains of modifiers/calls read as a pipeline, so they stay in application order (`Modifier.fillMaxSize().background(ComposeColor.White)`, `super.onCreate(savedInstanceState)`) — sorting the receivers would read as a bug.

## KD (Kotlin Dialect) reference — see ref/kotlin-dialect

We're porting this to Swift as dialect v4

- **Redux-like architecture**: Controller/Context (Store), Shoulds (Reducers), Effects
- **KDContext** protocol: `recentField: String`, `field<T>(name)`, `fieldAny(name)`, `selfCopy()`, `setField(name, value)` — selfCopy lets the controller treat derived contexts uniformly
- **KDController**: accumulates a `queue` of context snapshots, each with `recentField` set. `set()` copies context, applies mutation, queues it, runs `processQueue()`. `executeFunctions()` applies queued mutation then runs every should-function; a function re-queues only if it changed a field (`recentField != KD_FIELD_NONE ("none")`). Recursion blocked via `isProcessingQueue`.
- **Should-functions (reducers)**: receive a context copy, return a new context. SSOT rule: **only one should-function may write a given field** (name them `shouldReset<FieldName>` style; combine branches that write the same field into one function, e.g. `cliShouldResetConsoleOutput` holds both "no file arg" and "input error" branches).
- **CLIError**: enum in `components/cli/cliAux.swift` (conforming to Error) for should/effect error signaling; effect funcs `throw` rather than doing multiple `cliSet` writes, so each field has exactly one write site.
- **Entity types** in kd.yml: `context`, `struct`, `should`; fields typed; `output:` section declares codegen targets (`type: kotlin|swift|c++hdr|c++sdk|c++src|jsexport`); `prefix-kotlin`/`raw*` for code insertion; `F` struct holds field-name string constants used in conditions like `c.recentField == F.didSetup`.
- **Klin**: Original KD codegen is a Node.js app built from Kotlin. Dialect v4 is reimplementing this in Swift.
